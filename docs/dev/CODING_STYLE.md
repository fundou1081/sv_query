# 编码风格与设计决策 (Coding Style & Decision Logic)

> **本文是 `AGENTS.md` 的细则文件之一。** 入口/索引见 [AGENTS.md](../../AGENTS.md)。
> 硬性禁止项在 [DISCIPLINE.md](DISCIPLINE.md)；提交前检查在 [REVIEW_CHECKLIST.md](REVIEW_CHECKLIST.md)。
> **最后修订**: 2026-10-19

写代码前先想清楚"**该怎么做**"，而不是"能不能跑通"。

---

## 1. 先探索，后决策

- 动手改之前先读：相关模块、调用方、已有的同类实现
- 至少给出 **2 个方案**，说明为什么选这个 (而不是第一个想到的就写)
- **禁止**边猜边改 —— 猜测出来的改动等于引入未知

**可操作判定**: 如果被问到"这段代码在架构里属于哪层、做了什么、为什么存在、谁和它相关"
有一条答不上来，就还没到能改的时候。

---

## 2. 优先通用方案；同一个语义只写一份实现

- 优先选**对整类问题成立**的方案，而不是只对当前 case 成立的补丁
- 如果一个改法要为 case A / case B 各写一个分支 → 说明抽象层选错了，回退重想
- 特判必须有注释说明"为什么这里**天然**是特例"
- **发现同一语义有两份实现 → 合并或删除，不要"两份都改对"**：

| 项目 | 后果 |
|---|---|
| 保留两份实现 + 分别对齐 | 下一次改动只改一处 → 立刻分叉 |
| 删除一份，另一份做薄适配层 | 不可能分叉；再用**结构性测试**锁住"不许再长回来" |

**真实案例 (iter_240/241)**: `loads` 有 `SignalTracer.trace_fanout`（CLI 走这条）与
`LoadTracer`（API 走这条）两份遍历。前者修好了跨模块，后者还自己拼 id
(`f"{module}.{signal}"` → `"None.sig"`)，于是 API 对任何不给 module 的查询都**静默返回空**。
修法不是"把第二份也改对"，而是把 `LoadTracer` 改成薄适配层 + 删掉死基类，
并加结构性断言：`LoadTracer` 不得再出现私有遍历方法、`graph_traversal` 模块不得复活。

---

## 3. 修 bug 要修到根因

| 层次 | 表现 | 是否可接受 |
|---|---|---|
| 症状层 | 改断言 / 加 `try-except` / 加特判绕过 | ❌ 禁止 |
| 行为层 | 修正这个函数的输出 | ⚠️ 仅当根因确实在此 |
| 根因层 | 修正数据结构 / 契约 / 调用时机 | ✅ 目标 |

修完必须能回答：**"同类 bug 还会不会再出现？"** 答案必须是"不会"，并给出依据
(机械检查 / 结构性测试 / 契约变更)。

**配套要求**: 根因修复要留**回归锁**——
- 能机械化检查的 → 写进 `tools/` 检查器 ([WORKFLOW.md](WORKFLOW.md) §5)
- 行为契约 → 写成测试，特别是**反向断言**（"不应该出现的节点不出现"）

---

## 4. 看到架构方向的问题就停下

- 当"这个 bug 是架构缺陷的必然产物"时 → **停下来报告**，不要在错的架构上继续打补丁
- 危险信号：
  - 反复在同一处修 bug
  - 修一处坏三处
  - 每个新功能都要改同一个巨型函数

---

## 5. 函数要简洁

- 一个函数**只做一件事**，命名能说清它做什么
- 经验阈值：超过 ~50 行 / 嵌套超过 3 层 / 需要滚动才能读完 → 考虑拆分
- 禁止"什么都干"的巨型函数 (parse + transform + validate + write 混在一起)
- 拆分依据是**职责**，不是行数 —— 不要为了凑行数硬拆出无意义的辅助函数

---

## 6. 结构化数据优于字符串

- 用 `dataclass` / `NamedTuple` / `Enum` / `dict`；不要把结构信息编码进字符串再 `split()` 取回来
- 字符串只用于：最终输出、日志、用户可见文本
- 这条与"禁止 string fallback"是同一原则的两面

**反例**: 用 `"mod.inst.sig"` 当数据载体在各层之间传递 —— 一旦某段名字里含 `.`
(如 generate 路径、结构体字段、参数化 class)，解析就崩，且错误出现在很远的地方。

---

## 7. 决策前评估影响范围

改动之前先确认：

- 谁调用了它 (全仓 `grep`：函数名 / 类名 / 常量名，以及按路径读源码的地方)
- 改了返回类型 / 语义，下游会不会静默出错
- 有没有测试覆盖这条路径 (没有 → 见 §9)
- 是否影响已有的 truth / baseline / 基准

**影响范围不明确时，先查清楚再改**，不要"改了跑测试看看"。
需要机械扫描时用 `python3 tools/find_module_refs.py`（它能列出 `from X import Y`、
按路径读源码、`__file__` 深度运算这三类易漏引用）。

---

## 8. 注释与 docstring

- **注释写"为什么"，不写"是什么"** —— 代码已经说明做了什么
- 修复类改动要留下**日期 + 迭代号 + 原因**，例：
  `# [iter_241] LoadTracer 现在是薄适配层, 同样需要 mig`
- 契约不明显的函数要写 docstring：输入**形态**（尤其是 `None` 的含义）、返回、失败语义
- **禁止**写过期注释：删掉的类/函数名留在 docstring 里等于埋雷 (iter_241 顺带清理了两处
  引用已删除 `TraceResult` 的 docstring)

---

## 9. 发现缺少测试要主动说

写代码时发现某条路径没有覆盖 → **主动告知方豆**，并说明：

- 哪个函数 / 分支没覆盖
- 建议补什么级别 (unit / cli / truth / 真实项目冒烟)
- 成本估计

**不要**默默跳过，也不要未经确认就大批量补测试。

**优先级判断**: 这条路径是否被**真实项目**用过？
本项目已经三次验证"fixture 全绿 ≠ 功能正确"——只测 fixture 会漏掉真实 filelist 的形态。

---

## 10. 日志与错误

- 失败必须**可见**：`logger.warning` (业务可容忍) / `logger.error` (应当修) / `raise` (契约破坏)
- 捕获异常时必须给出**上下文**：`logger.debug("MIG internal 查询失败: %s", e)`
- 查询类 API 的"查不到"与"出错"必须用**不同返回值**表达 (sentinel vs 异常)
- **禁止**用日志代替返回值契约（日志没人看，调用方会拿到 `None`）

---

## 11. 与方豆的协作规则

### 11.1 主动告知

发现下面任何一项时**主动、明确**地告诉方豆，不要自己默默决定或跳过。
说明要包含：**现状 → 问题 → 建议 → 代价**，然后**等方豆决定**。

| 发现 | 应该说什么 |
|---|---|
| 缺少测试 | 哪条路径没覆盖、建议什么级别 |
| 有更好的架构 | 当前缺陷、更好的结构、迁移成本 |
| 有更好的解决方案 | 现方案的局限、替代方案、取舍 |
| 有更简洁的实现 | 冗余点、简化形态、行为是否等价 |
| 有更高效的算法 | 当前复杂度、能优化到多少、是否真是瓶颈 |
| 登记过的"已知局限"实际更严重 | 实测证据 + 真实影响面 (案例：iter_241 的 `LoadTracer`) |

**原则**:
- 告知 ≠ 擅自动手 —— 大改动 (架构 / 重构 / 换算法) 必须**先说后做**
- 小而安全的改进 (改名、拆函数、去冗余) 可以直接做，但要在总结里**列出来**
- 宁可多说一句，不要"我觉得这样更好所以就改了"

### 11.2 用户决策与已有事实冲突 → 反复确认

- **不要默默照做**，也不要默默按自己的理解改
- **明确指出冲突点**："你说的 A，但 `<文件:行>` 显示的是 B"
- **说明照做的后果**：会破坏什么、影响哪些测试、有什么风险
- 反复确认，直到方豆明确知情并拍板

### 11.3 新决策与旧决策冲突 → 停下来问

- **立即停止**，不要"先做着看"
- 列出：旧决策 (出处) + 新决策 + 矛盾在哪
- 等方豆明确答复再继续

**理由**: 在矛盾的前提下继续开发，产出必然返工，而且会污染后续所有决策。
