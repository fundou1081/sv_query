## 一、项目概览

**要解决的问题**: AI agent / 验证流程在阅读 RTL 时缺乏一个"给出机器可验证事实"的查询层。LLM 直接读源码会幻觉，波形工具只回答"值是什么"而非"结构上谁驱动谁"。sv_query 定位为 agent 的 SystemVerilog 语义查询 + 客观校验层。

**目标用户**:

- 主要: AI agent、脚本化验证流程（CLI JSON 是一等公民）
- 次要: 验证工程师、RTL 阅读者（人类可读输出为辅）

**核心流程**（Scope → Trace → Verify 分层工作流，见 `product_direction_2026-10-31.md`）:

```
scope 定位候选与 canonical ID
  → trace 追定义/连接/条件/时间
  → evidence 钉源码
  → verify 确认/反驳
```

**技术实现链路**:

```
CLI (Typer) / Node agent tool
  → UnifiedTracer (声明式 Pipeline, src/sv_query/trace/unified_tracer.py)
  → SVCompiler (pyslang semantic AST, src/sv_query/trace/core/compiler.py)
  → SemanticAdapter (mixin 组合, src/sv_query/trace/core/semantic_adapter.py)
  → GraphBuilder (16-stage GraphPipeline, src/sv_query/trace/core/graph_builder.py)
  → SignalGraph + ModuleInstanceGraph
  → PathResolver / SignalTracer / DataFlowGraph / verify
  → stable JSON（truncated/unknown/verified 显式标注）
```

产品分层: `Scope/Inventory`、`Trace/Causality`、`Verify`、`Locate`、`State(snapshot)`、`exp`(默认隐藏、无稳定契约)。

## 二、目标合理性判断: **合理且清晰**

判断依据:

1. **产品边界收窄得正确**（`product_direction_2026-10-31.md`）: 不做通用 NL 解释器、不替代波形工具、动态 debug 只提供 canonical ID + evidence，值留给外部工具。这是对"LLM 读 RTL"这一真实痛点最保守、最可防御的切入方式。
2. **"防幻觉"需求倒逼出的架构是对的**: 要机器可验证事实 → semantic AST + graph + evidence 源码行号; 要 agent 可发现 → `capabilities` + `json_contract` 机器可读契约（`src/cli/_registry.py`）; 要不撒谎 → explicit unknown/truncated 状态机。手段与目的一致，没有为了技术而技术。
3. **实现与目标匹配度高**: P158 之后，`src/sv_query/trace/core/graph/contracts.py` 是 edge 分类的唯一实现（数据边 DRIVER/CONNECTION、控制边 CLOCK/RESET/BRANCH_*/CASE_*、结构边 BIT_SELECT/MEMBER_SELECT），`PathResolver`、`verify.py`、`dataflow.py` 全部引用同一策略源; `sim/tests/unit/test_p158_data_edge_contract.py` 含 true-positive 和 mutation 测试（monkeypatch 注入 CLOCK 到 DATA_EDGE_KINDS 断言失败）——这是"单一定义 + 多面消费 + 反向验证"的正确形态。

## 四、缺点与风险（附代码证据）

### P0 级（正确性/可靠性）

1. **`DataFlowGraph._find_paths()` 无工作预算**（`src/sv_query/trace/core/graph/dataflow.py`）:
   仍用 `nx.all_simple_paths(cutoff=...)`，只有深度 cutoff 没有 expansion budget/deadline; `analyze()` 在枚举完成后才 `paths[:max_paths]`，防不住枚举过程本身爆炸。这是唯一仍在违反自家语义契约（"路径必须有 budget/timeout"）的活代码，对应待办 **P158.11.2b**。
2. **snapshot 精度不完全对齐 live graph**（`src/sv_query/trace/core/graph/models.py` 的 `SignalGraph.to_dict()`）:
   未序列化 `condition_chain`、`effective_condition`、`source`、`function_return`、`is_function_call`、`extra` 等 edge 字段。旧 snapshot 查询与 live 查询可能给出不同细节，与"单一事实源"纪律有张力，对应待办 **P158.9**。

### P1 级（性能）

3. **`SignalTracer` 全图边扫描**（`src/sv_query/trace/core/query/signal.py`）:
   `_find_drivers()` 等处 `for src, dst in list(self.graph.edges())` 逐个比对 `dst == signal_id`，大图上退化 O(V×E)。当前语料（万级边）未触发，但 10 万边级设计会成为瓶颈。`src/sv_query/trace/core/query/structural.py` 的 `_port_map()` 是 O(instances×E)，同类问题。
4. **agent neighborhood 工具的进程模型**（`tools/agent/svq-query-tool/index.js`）:
   每展开一个节点就 `execFile` 启动一次 Python CLI 子进程并重新加载 snapshot。BFS depth 4、100 节点即百次冷启动。对小意图够用，对深度探索是数量级瓶颈。

### P2 级（可维护性/分发）

5. **packaging 布局是最大结构性技术债**:
   top-level `trace` 包与 Python 标准库 `trace` 模块同名，靠 `src/cli/_entry.py` 的 `sys.path.insert` 规避; `pyproject.toml` 的 packages.find 混合 `src.*` 与 `trace*`/`cli*`。开源分发时这是最容易被踩的雷。
6. **大文件集中**:
   `graph_builder.py` ~2298 行（16 stage 仍单大类，且注释写"12 个 pass"已漂移）; `signal.py` ~1970 行; `semantic_adapter.py` 靠 mixin 拆分但底层 pyslang API 动态访问导致大量 safe wrapper。
7. **文档状态漂移**:
   README 写 `2571 passed / 2026-11-05` 而 `docs/INDEX.md` 基线是 2678 passed; `CURRENT_TODO.md` 头部停在 P152 而 git log 已到 P163; 根目录 `package.json`（version 1.0.0、test script 是错误提示、依赖 elkjs）是历史遗留，易与 `tools/agent/svq-query-tool/package.json` 混淆。

### P2 级（验证外部效度）

8. **corpus 主要是自撰**:
   external fault set、真实 bug 修复效果、成本优势均未验证（`FINAL_VALIDATION_SUMMARY` 自己也明确列了这四项）。OpenTitan filelist 依赖闭包仍是人工整理，是真实项目可复现性的最大缺口。

## 五、替代方案比较

### 方案 A: LLM 直接读源码 + 检索（RAG）

- **收益**: 实现成本最低，覆盖任意自由问题。
- **成本**: 幻觉不可消除; T2 vs source 的 48/48 vs 32/48 对照恰恰量化了这条路的信息损失。
- **结论**: **不替代**，只作为 sv_query 之外的补充层（agent 已可这样做）。

### 方案 B: 基于 Verilator/Yosys 等成熟工具的 IR 而非 pyslang

- **收益**: 工业级解析鲁棒性; Yosys JSON 后端可复用。
- **成本**: Verilator 面向仿真（无 class/constraint 语义）、Yosys 面向综合（会抹掉验证结构）; 重写 adapter 层约数千行; 失去 pyslang 可编程 semantic AST 的灵活性。
- **适用条件**: 若未来重心从"验证语义查询"移向"综合后结构查询"，可作局部补充（如 fanout 物理优化）。
- **结论**: **迁移难度大、收益与目标错位，不建议**。当前 pyslang 选型与"class/constraint/covergroup 都要可见"的目标匹配。

### 方案 C: agent 工具从"每查询一个 CLI 子进程"改为常驻服务（daemon / in-process API）

- **收益**: neighborhood 类多跳查询成本从 O(节点数 × 冷启动) 降到 O(1) 冷启动，数量级改善。
- **成本**: 需要进程生命周期管理、并发/超时语义重定义; JSON schema 不变，agent 契约无破坏。
- **适用条件**: agent 实际使用中出现 >2 跳探索意图即可启动。
- **迁移难度**: 低——`svq-query-tool` 已把 `queryFn` 注入抽象好（`neighborhood.js` 纯函数式），只需换执行后端。
- **结论**: **推荐，性价比最高的架构演进**。

### 方案 D: SignalTracer/DataFlowGraph 改为预建索引（adjacency map / reversed index）

- **收益**: fanin 查询从 O(E) 扫描降到 O(度); 配合 NetworkX 已有的 `pred/succ` 视图，改动局部。
- **成本**: 每张图多一份索引内存（约与边数线性）; 图构建后只读，同步成本低。
- **结论**: **推荐，低成本高确定性**。

## 七、结论

**当前方案值得保留，且方向正确。** 这是一个目标定义罕见清晰、纪律执行罕见严格的项目: 产品边界主动收窄、语义契约单一定义并有多面消费、验证状态机结构上禁止说谎、诚实维护 KNOWN_LIMITATIONS。核心架构（semantic AST → graph → bounded query → explicit contract）与"给 agent 提供可验证事实"的目标高度匹配，**不需要推倒重来**。

需要做的不是换方案，而是**收敛和补课**:

- P158 留下的两个活缺口（dataflow 预算、snapshot surface）是仅有的正确性问题，应立即关闭;
- 性能与 packaging 是可预见的规模天花板，应在开源/扩大使用前处理;
- 外部效度（真实故障集）决定这套东西最终是"工程精良"还是"被证明有用"。
