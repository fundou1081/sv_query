# 第一部分：坑的账本

## 主题 A — 语义边界没有唯一定义

### A-1 `CLOCK` 被当成数据路径，`verified` 掉一条假路径 【已修 P158.1】

**现象**
```
paths top_minimal.sa1.clk top_minimal.sa1.ready_q --directed
  before: found=true, 1 hop, path [clk, ready_q]
  after:  found=false, mode=data

verify claim type=path  (同一对)
  before: verified
  after:  contradicted

dataflow analyze  (同一对)
  before: is_reachable=true, latency_cycles=1
  after:  is_reachable=false, paths_count=0
```

**根因**：三个消费者（`PathResolver` / `DataFlowGraph` / `verify`）各自维护 edge 策略，
且都接受**全部** edge kind。CLOCK/RESET 是控制边，不是数据边，但没有任何一处代码表达这层区别。

**当时的错误修法 / 失败尝试**
- 最早的直觉是"在 `PathResolver` 里把 CLOCK 过滤掉"。这能修 `paths`，但 `verify` 和 `dataflow`
  仍然各走各的路——**只修了一处，反而制造了三处不一致**。
- 真正的错误判断发生在更早：2026-11-09 的 P139~P142 阶段，我们把"路径"当成一个已定义的概念，
  从没问过"路径 = 数据边还是任意边"。**当时不知道有这个问题**，直到 11-11 的复盘才暴露。

**最终修法**
新增唯一实现 `src/trace/core/graph/contracts.py`：
```
DATA_EDGE_KINDS       = {DRIVER, CONNECTION}
CONTROL_EDGE_KINDS    = {CLOCK, RESET, BRANCH_*, CASE_*}
STRUCTURAL_EDGE_KINDS = {BIT_SELECT, MEMBER_SELECT}
```
所有消费者引用同一常量。契约禁止各命令写 `edge.kind in (...)`。
无向 `paths` 明确标 `mode:"structural"`。

**可复用预防措施**
1. 同一个语义只允许一份实现（铁律 I3）。发现"两份实现"时**先合并，不要分别修**。
2. 语义边界必须写进一个**可 import 的模块**，而不是散落在各命令里。
3. 契约类测试要断言三集合**互斥**，不只是断言某个集合包含某些值。

**证据**
- 实现：`src/trace/core/graph/contracts.py:42`（`DATA_EDGE_KINDS`）
- 消费方：`src/trace/core/graph/dataflow.py:25`、`src/cli/core/semantic/verify.py:24`、
  `src/trace/core/query/subgraph.py:12`、`src/trace/core/graph_builder.py:19`
- 回归：`sim/tests/unit/test_p158_data_edge_contract.py`（含 mutation：放宽 `DATA_EDGE_KINDS`
  必须让 guard 变红，见 `:455`）
- 文档：`docs/validation/P158_REMEDIATION_2026-11-11.md:8-52`
- 独立 oracle：测试文件 `:45-60` 用**手写的 fixture 语义**当 oracle（`clk` 在
  `always @(posedge clk)` 里只驱动时序，不驱动 `ready_q` 的数据），不是从实现反向生成

### A-2 `dataflow` 端点污染：`is_reachable:true` 但路径终点不是请求目标 【已修 P146】

**现象**
```
before: top_minimal.clk -> sa1.rst_n is_reachable=true, path ends at top_minimal.sa1
after:  is_reachable=false, paths_count=0
```
即：BIT_SELECT 的 **parent** 被当成了终点，路径最后落在父节点上，而不是用户请求的 dst。

**根因**：`DataFlowGraph.analyze` 在收集路径后没有校验终点。

**当时的错误修法 / 失败尝试**
- 先想到的是"过滤掉含 BIT_SELECT 的路径"。这会**误伤真实路径**——真实的 bit-select
  确实出现在数据路径里（比如 `cfg[3]` 驱动下游）。**判断错了**：BIT_SELECT 是结构边，
  但它可以出现在数据路径的**中间**，只是不能自己构成数据驱动。

**最终修法**：只过滤**端点**——`p[-1] == to_signal` 才算命中。

**可复用预防措施**
- "找到路径"和"路径到达了目标"是两件事，必须分别断言。
- 修一个假阳性时，先问"这个 pattern 在真阳性里是否也会出现"。会 → 修的位置就不对。

**证据**：`docs/validation/P146_REAL_MATRIX_2026-11-10.md` §4.1 (B1/M1)；
回归 `sim/tests/regression/test_dataflow_endpoint.py`（2 passed）

### A-3 三套 edge-kind 策略 → 一套 【已修 P158.1】

见 A-1。这是"边界概念没有唯一定义"的**元问题**：同一个词在不同层有不同实现。

| 词 | 当时的实际含义 | 现在的含义 |
|---|---|---|
| `directed` | PathResolver: 所有边 / SignalTracer: DRIVER+CONNECTION / frontier: 再加 BIT_SELECT | 统一 = data only |
| `verified` | total==0 且 status known，**不考虑 truncated** | 状态机，含 coverage 完整性 |
| `snapshot supported` | 有的命令支持有的不支持 | 能力矩阵（P158.9 待做） |
| `done` | 代码+测试+文档 | + 反事实 + 独立 oracle + 契约影响说明 |

## 主题 B — 证据等级与"假绿色"

### P-01 P157 的 "0 skipped" 是掩盖失败，不是质量提升 【未修 — 反模式已登记】

**现象**
```
before: canonical had 12 skips and 119 deselected
after:  canonical has 0 skips and 139 deselected
```
P157 把 12 个 skip 清理掉，canonical 变成 **0 skipped**，并写进文档作为成果。

**根因**：P157 的动作是——删掉 7 个已退休命令（`exp backpressure deadlock`）的 deadlock 测试，
把 2 个 long-range 测试和 3 个 benchmark PR5 测试标记为 `pytest.mark.opensource`。
其中约 20 个测试被移出 canonical 统计。

**当时的错误修法 / 失败尝试 —— 这条必须写清楚**
我们当时的推理是："canonical 里应该有明确理由的 skip，不该有未解释的 skip。"
这个目标本身没错。**判断错的是执行方式**：我们把"移出 canonical"当成了处理方式，
而没有先问"**这些测试为什么失败**"。

结果就是：**20 个测试被移出统计口径，其中约 28% 本身是失败的。**

**`[复核]` 我在本文写作时实际跑了一遍 opensource 套件**：
```
$ python3 -m pytest sim/tests/ -m "opensource" -q
38 failed, 97 passed, 6 skipped, 2668 deselected, 3 warnings in 365.92s
```
38/141 ≈ **27% 失败率**，与当时记的"约 28%"吻合。
（另有 6 个 skip 仍然留在 opensource 集合里——说明连"移出去"也不是干净的归类。）

**后续（2026-11-11 P161）**：opensource 已从 38 failed 修到 0 failed / 114 passed / 17 skipped。
P157 的“0 skipped”仍然是错误指标，但 opensource 不再有 27% 红色。
**当时是否仍未修**
- 当时**仍未修**。P157 本身没有回滚，canonical 数字仍然是 "0 skipped"。
- 部分补救：`CLAIMS.md` C-10 明确登记 `"canonical 0 skipped 代表测试健康"` 为
  **`known-broken`**，并注明原因是 "P157 移出失败测试"。
- 真正的修法是 `REVIEW_2026-11-11.md` §5.5 定义的指标重新定义：
  ```
  passed / failed / unknown / truncated / unexecuted / skipped-with-reason / external-not-run
  ```
  这条尚未落地（P158.12 待做）。

**可复用预防措施**
1. **"0 skipped" 不是 KPI，是危险信号。** skip 的合理处置是"说明为什么跳过 + 单独报告"，
   不是"移出统计"。
2. 任何把测试移出统计口径的 PR，必须在 PR 里给出：移出数量、其中失败数量、单独运行结果。
3. 报告绿色的口径必须分离：`passed / failed / unknown / skipped / unexecuted` 分开列。

**证据**
- 动作记录：`docs/validation/P157_SKIP_CLEANUP_2026-11-11.md`（它自己也写了
  "这不代表外部测试通过"——但这句没被写进任何 claim）
- 复盘定性：`docs/validation/REVIEW_2026-11-11.md:56`（R-009）、

- 台账：`docs/dev/CLAIMS.md:33`（C-10 `known-broken`）
- `[复核]` 上面的 opensource 实跑输出

### P-02 worker 的 APPROVE 不是证据；一次 fresh parse 不能证明 determinism 【部分修】

**现象**
- P147 worker：`verdict: APPROVE`，SPI-T1..T6 全过。
- P152 worker：`verdict: APPROVE WITH NITS`，9 tasks / 16 assertions 全过，
  并报告 "fresh parse 与 snapshot 结果在一次采样中一致"。
- 但主会话独立复现时发现：**同一份 SPI 源码/filelist 连建两次，nodes/edges 就不同**
  （7618/7620 nodes，12375/12377 edges）。

**根因（两层）**
1. 评测流程层：worker 的"独立"只是**访问独立**——代码、快照、假设都是同一份。
   一次观察被写成了 "byte-identical" 的结论。
2. 实现层：构建本身**确实不确定**（根因见 P-04）。

**当时的错误修法 / 失败尝试**
- 我们当时接受了这个措辞，直接把 P152 的结论写进验证文档。**判断错了**：
  worker 说 "一致" 被我们理解成 "确定性成立"，而 worker 只做了一次采样。
- 纠正出现在 11-11 复盘：`REVIEW_2026-11-11.md:129` 直接点名
  "'APPROVE WITH NITS' 被当成真实项目通过，但 worker 的 fresh/snapshot 只跑了一次"。

**最终修法 / 是否仍未修**
- 流程侧**已修**：`SEMANTIC_CONTRACTS.md` §10 明确
  "一次 fresh parse 不能证明 determinism"、"'独立'指 **oracle 独立**，不只是访问独立"；
  `CLAIMS.md` C-12 把 "worker APPROVE 等于真实项目通过" 标为 **`known-broken`**。
- 实现侧：真正的确定性修复见 P-04。
- **仍未修**：worker 的审批流程本身没有强制要求"可复现命令 + 实际输出 + 至少一个反例"，
  目前只是写在契约文档里，没有机械检查器。

**可复用预防措施**
1. 评审结论必须区分 **"我观测到"** 和 **"我推断"**。
2. N 次重复才配叫"确定性"。3 次是最低线（我们最后用的是 5 次，`test_determinism.py:39`）。
3. worker 报 APPROVE 后，主会话**至少独立复现 P0**。

**证据**：`docs/dev/SEMANTIC_CONTRACTS.md:291-299`；`docs/dev/CLAIMS.md:35`；
`docs/validation/REVIEW_2026-11-11.md:129`

### P-03 测试是实现的镜像，不是独立规格 【已修 P158.8】

**现象**
- P152 corpus 的 `expected` **大量由 CLI 反向生成**（先跑一次，把输出抄成期望）。
- `test_path_directed_parity` 只证明 `paths` 与 `dataflow` **一致**，不证明它们**正确**。
- bit / reciprocity 检查**只有"没有误报"的测试**——把 `_check_bit_mapping` /
  `_check_reciprocity` 整个关掉，测试**仍然全绿**。

**根因**：这是"自我确认"闭环：
```
实现有 bug → 测试按实现写 → 测试通过 → 认为实现正确
```

**当时的错误修法 / 失败尝试**
- P152 当时给了 worker 两个修正任务（P153 transitive fanin、P155 reciprocity），
  都是**修实现**。我们默认"测试已经覆盖了"。**当时不知道测试是空的**——
  直到复盘时用 mutation 试了一下才发现关掉检查测试还是绿。

**最终修法**
- `SEMANTIC_CONTRACTS.md` §8.3 规定每个验证器必须有 4 件套：
  ```
  true-negative（没错误不报）
  true-positive（构造真实错误必须报）
  mutation（关闭实现，测试必须红）
  independent oracle（期望不由同一实现生成）
  ```
- P158.8 补齐：bit_mapping 的真实 width/range 不一致、reciprocity 的真实不对称 fanin、
  legacy snapshot 的显式 unknown 回归。
- `CLAIMS.md` C-11 给出 `scoped` 证据等级（`--full` 实测 3152/3261/1734，0 violations），
  而不是一个笼统的"全绿"。

**可复用预防措施**
1. **每个检查器写完当天，就要问：把检查器关掉，测试会不会红？** 不会 → 测试没在测它。
2. `expected` 不许由被测命令生成。真实项目的 `expected` 从 RTL 人工读出来并写明行号。
3. "一致" ≠ "正确"。parity 测试是必要条件，不是充分条件。

**证据**：`docs/validation/REVIEW_2026-11-11.md:114-123`（§3.2）；
`docs/dev/SEMANTIC_CONTRACTS.md:259-269`；
P158.8 实现：`sim/tests/unit/test_verify_bit_width.py`（+16 行）、
`sim/tests/unit/test_verify_reciprocity.py`（+19 行）、
`sim/tests/regression/test_verify_consistency_snapshot.py`（+21 行）
（见 `git show --stat 75725e65`）

### P-04 构建不确定性：`id(pyslang wrapper)` 被 GC 地址复用 【已修 P158.3，含一次失败尝试】

**现象**
```
同一 SPI 源/filelist，连续两次构建:
  7618 nodes / 12375 edges
  7620 nodes / 12377 edges
```
P152 当时写下的 "byte-identical" 不成立。

**根因**
`SemanticAdapter._genvar_context` / `_primitive_genvar_context` 用 **`id(pyslang wrapper)`** 作 key。
pyslang wrapper 是**临时对象**；CPython GC 回收后地址会被复用，不同 AST 节点撞上同一个 key，
genvar/scope context 错位 → 同一输入建出不同的图。

**当时的错误修法 / 失败尝试 —— 这条是本文最值得记住的技术失败**
> **失败尝试：改用源码位置（source location）作为 context key。**
>
> 想法是"用语义位置代替不稳定的对象身份"，比 `id()` 稳定得多。
> **结果：失败。** `generate` for 循环展开出来的多个项**共享同一个源码位置**，
> 于是所有展开项的 genvar context 全部塌缩成同一个值。
> **实测 18 个测试失败**，方案被回退。
>
> 这是个典型的"两个修法共享一个前提"（ub-mode 说的 Attack the Premise）：
> 位置**唯一**但**不区分身份**；`id()` 唯一但**不稳定**。
> 正确解法不是二选一，而是**保留 `id()` 的 per-entry 语义，同时保证被取 id 的对象活着**。

**最终修法**
登记 context 的同时**持有 wrapper 的强引用**（`_ast_ctx_refs`），
使 `id()` 在 context 生命周期内唯一——不改变原有 per-entry id 语义。
```python
self._ast_ctx_refs.append(node)          # [P158.3] keep id() unique
self._genvar_context[id(node)] = dict(ctx)
```
```python
self._ast_ctx_refs.append(node)          # [P158.3] keep id() unique
self._primitive_genvar_context[id(node)] = dict(ctx)
```

**结果**
```
before: 7618/7620 nodes, 12375/12377 edges
after:  7621 nodes, 12377 edges（连续 3 次一致；回归测试用 5 次）
```

**可复用预防措施**
1. 用 `id()` 做 key 时，**必须同时持有被引用对象的强引用**。这是一个很容易忘、也很难查的 bug。
2. "稳定的位置"不等于"稳定的身份"。generate 展开会共享位置。
3. 确定性测试要 **N 次重复 + canonical hash**，不是比 count。

**证据**
- 修复点：`src/trace/core/semantic/exprs_drivers.py:179`、`:192`；
  `src/trace/core/semantic/modules.py:432`
- 回归：`sim/tests/regression/test_determinism.py`（5 次构建 + sha256 canonical hash，
  见 `:23-44`）；`sim/tests/regression/test_ast_identity.py`

## 主题 C — 有界性、性能与可靠性

### C-1 无向 `paths` 指数爆炸，30 秒不返回 【已修 P158.2】

**现象**
```
SPI 7.6k 节点上:
  before: >30s / 无输出
  after:  0.6s, found=true, truncated=true,
          truncation_reason=max_expansions_reached
```
P146 时 UART 4.8k 节点上默认无向 `paths --canonical` 也能"无限运行"，
当时是靠加 `--max-depth`（默认 50）缓解的，UART 实测 ~6s。

**根因**：无向路径枚举在有环图上是组合爆炸，depth 不是 work budget。

**当时的错误修法 / 失败尝试**
- **第一次尝试（错）**：加 `--max-depth`。这解决了 UART，但没有解决根因——
  depth 限制的是路径长度，不是搜索量。**判断错了**：把"深度"当成了"预算"。
  契约里现在明写："不允许用'降低默认 depth'假装有界；depth 不是 work budget"。
- SPI 上仍然 30s+ 无返回，直到 P158.2 才真正修好。

**最终修法**
`PathResolver.find_all_paths_detailed` 增加：
- `max_expansions`（work budget，默认 200_000）
- `deadline`（wall-clock）
- 输出 `truncated` / `truncation_reason` / `expansions`
- CLI: `paths --max-expansions N --timeout S`
- 截断原因枚举：`max_paths_reached` / `max_depth_reached` / `max_expansions_reached` / `deadline_reached`
- **超限不能返回 `found:false`**，必须返回 `truncated:true` + 原因，
  或 `ok:false` + `unknown_kind:"search_budget_exhausted"`

**可复用预防措施**
1. 任何图遍历都要有 **work budget + wall-clock timeout** 双保险。
2. 截断是**一等状态**，不是错误：`truncated` 必须出现在输出 schema 里。
3. "没找到" 和 "没查完" 必须是两个不同的返回值。

**证据**：`src/trace/core/module_instance_graph.py:485-530`（`_SearchBudget` 在 `:312-343`）；
CLI `src/cli/core/semantic/paths.py:40`；
`docs/dev/SEMANTIC_CONTRACTS.md:110-124`；

### C-2 `verify consistency` 在 sample/truncated 上仍顶层 `verified:true` 【已修 P158.6】

**现象**
```
SPI reciprocity:
  checked 32 / skipped 168 / truncated true
  但顶层 verified = true
```
即：**只检查了 32 项，声称全部通过**。

**根因**：`verified` 的判定条件只有 "total == 0 且所有 check status known"，
**没有考虑 coverage 是否完整**。`truncated` 这个信息被算出来了，却没有参与顶层判定。

**当时的错误修法 / 失败尝试**
- 早期（P146 I14）我们把它记为"已知限制：默认 sample 易被误读为 pass"——
  **记录了，但没修**。这正是复盘说的"局部修复没有全局不变量"：
  我们知道它有影响，选择写进文档而不是修。
- 另一个更早的错误：P148 我们**单独修了 width 语义**，却没问"verified 的聚合逻辑本身对不对"。

**最终修法**
`verify` 引入 `coverage_complete`：
```python
partial_checks = [c["check"] for c in results if c.get("truncated") is True]
coverage_complete = not partial_checks
"verified": total == 0 and all_known and coverage_complete,
"coverage_complete": coverage_complete,
"partial_checks": partial_checks,
```
sample/truncated → `verified:false` + `partial_checks`。

**可复用预防措施**
1. **sample/truncated 永远不得写成 verified**（现在是铁律 13）。
2. 顶层状态是所有 requested checks 的**聚合**，不能用单项 pass 冒充全部通过。
3. `unknown_checks` 非空 → 顶层必须 false。

**证据**：`src/cli/core/semantic/verify.py:413-425`；
`docs/validation/P158_REMEDIATION_2026-11-11.md:138-144`；
回归 `sim/tests/unit/test_verify_truncated.py`；
`docs/dev/SEMANTIC_CONTRACTS.md:128-176`

### H-1 capabilities / json_contract / AGENT_FEATURE_MAP 三处不一致 【部分修 P158.9】

## 主题 I — worker 协作的运维坑

### I-1 配额中断 / worker 越界 / 迟到反馈 【部分修】

**现象**
1. **MiniMax 429** 导致两个 worker 中断；DeepSeek 免费额度在 P146 再次耗尽，
   那轮独立 worker 主要靠 MiniMax。
2. **一个 worker 误改了 `AGENTS.md`**，并在仓库里留下 repro 脚本——
   主会话必须清理 + 复核。
3. **迟到的 worker**：P146 的 UART worker 在 P146 **标记完成之后**才返回，

**根因**：多 agent 没有隔离协议——worker 的工作目录、权限、提交边界没有强制约束；

**当时的错误修法 / 失败尝试**
- 当时我们把 worker 迟到当作偶发。**判断错了**：晚到的 worker 报告的正是**主会话自己看不见的缺陷**，

**最终修法 / 是否仍未修**
- 部分：P146 §4.1 单列"迟到的 UART worker：BLOCK 的两个真实缺陷"，并补了回归测试。
- **仍未修**：没有机制保证"所有 worker 反馈已回收"才允许标完成。

**可复用预防措施**
1. 标完成前，确认**所有已派出的 worker 都已返回**（包括迟到的）。
2. worker 的写权限应限制在自己的 worktree；改 `AGENTS.md` / 规则文件需要显式授权。
3. worker 产出要单独 review，尤其是"改动了纪律文件"这类越界行为。

### I-2 `verify driver` 与 `verify path` 对同一对信号结论矛盾 【已知限制，未修】

**现象**

**当时的处理**

**证据**：`docs/validation/P146_REAL_MATRIX_2026-11-10.md` §2、§3 (I3)

### I-3 `verify claim driver` 默认 depth=1，transitive 被 contradicted 【已修 P153，文档仍待修】

**现象**
`verify claim driver ... --transitive` 返回 **contradicted（假）**：
`u_fsm.sck_o` 是 `u_spi_core.sck_o` 的 wrapper_passthrough 源，
但 `trace_fanin(cio_sck_o, depth=None)` 的结果里**不含** `u_fsm.sck_o`。

**根因**：`_handle_port_out_source` 对 wrapper 源只调 `_recurse_if_unseen`，
**没有先把该 PORT_OUT 源 append 到 drivers**；该节点进了 `seen_ids` 之后再也不会被追加。

**最终修法**
对 wrapper_passthrough 源改用 `_append_source`：先 append 源节点，再递归。
depth=1 的 contradicted 语义不变（不是关闭检查）。

**可复用预防措施**
- "seen" 集合在**加入输出**之前就把节点标记掉，是一个经典 bug 形状。
- 修 fanin 保留问题时，要同时验证 direct（depth=1）语义没被改。

**证据**：`docs/validation/P153_TRANSITIVE_FANIN_2026-11-10.md`；
回归 `sim/tests/usage/test_transitive_wrapper_fanin.py`

### I-4 `verify consistency` 的 width / parent 误报（generate 路径）【已修 P148 + P150】

**现象**
SPI_HOST 上 `bit` 检查报 **728** 条 width mismatch。修 width 后剩 **171** 条
`id_parent_mismatch`，再修 parent 后剩 **0**。

**根因（两处）**
1. **width**：图里单 bit 节点可能存 `(1, 0)` 默认 sentinel（实际是 1 bit），
   而公式 `abs(width_msb - width_lsb) + 1` 把它算成 2 bit。
2. **parent**：旧检查 `if "[" in n and not n.startswith(parent + "[")` 把
   **祖先路径里的 generate 下标**（如 `prim_ram_1p_adv.gen_ram_inst[0].u_mem.cfg_i.ram_cfg`）
   误当成 bit-select。

**当时的错误修法 / 失败尝试**
- P147 worker 的建议是"改 `nbits`"。我们当时就指出：**不能把 `(1,0)` 一律当 1 bit**，
  否则真实 2-bit 会被误判——worker 建议的直接照做会引入新 bug。
  最终改成"**单 bit 场景用显式 span**"：bit_range 不含 `:` 或
  `parent_bit_start == parent_bit_end` → `nbits = 1`，其余仍用公式。

**可复用预防措施**
1. 修一个误报时，问"**同样的 pattern 在真阳性里合法吗**"。
2. generate / struct 路径里的 `[` 与 bit-select 的 `[` 必须区分——
   只看**相对 parent 的直接关系**。

**证据**：`docs/validation/P148_VERIFY_WIDTH_2026-11-10.md`；
`docs/validation/P150_ID_PARENT_2026-11-10.md`；
`sim/tests/unit/test_verify_bit_width.py`（3 passed）

### I-5 reciprocity 把 BIT_SELECT 结构边当数据边 【已修 P155】

**现象**
SPI_HOST `verify consistency --checks reciprocity`：
```
sample: 9 violations
--full: 128 violations
```
全部落在 `prim_arbiter_tree` / `prim_alert_sender` 的 generate 层次，
**不是 SPI_HOST 的逻辑问题**。

**根因**：`trace_fanin` 会返回 **BIT_SELECT 结构边**（generate/struct child → parent），
而 `trace_fanout` 不把这种层次边当数据负载。reciprocity 却直接拿两者比较 → 假 `fanin_not_reciprocal`。

**最终修法**
reciprocity 只比较 DRIVER / CONNECTION 数据边：
```python
def _has_data_edge(graph, a, b):
    return any(e.kind.name in ("DRIVER", "CONNECTION")
               for e in graph.get_edges(a, b))
```
结果：`sample 9 → 0`，`--full 128 → 0`。

**可复用预防措施**
- 互逆性检查的两端必须**用同一套边定义**。这次是 fanin/fanout 用了不同定义。
- **这不是关闭检查**——真实 DRIVER/CONNECTION 不互逆仍会报（P158.8 加了 true-positive 保护）。

**证据**：`docs/validation/P155_RECIPROCITY_2026-11-10.md`；
`sim/tests/unit/test_verify_reciprocity.py`

# 第二部分：正面经验

## 1. 语义提取走 pyslang semantic AST，禁止源码 regex（唯一例外：UVM 宏）

**为什么有效**：class / constraint / covergroup / UVM 的语义事实必须来自语义模型。
UVM 是**唯一例外**，因为 pyslang 预处理后 macro invocation 不在 semantic syntax 中
（实测 `str(class.syntax)` 在 `uvm_object_utils` 位置为空，`SyntaxTree` 也没有 `MacroUsage` 节点）。
UVM regex 只允许放在 `src/trace/core/query/uvm.py`，结果必须标 `confidence: "syntactic"`，不得当 verify 证明。

**机械保障**：`tools/check_semantic_regex.py`，检查器自带"能检出违规"的自检。

## 2. 禁 `--no-strict`、禁 silent fallback、禁 `except: pass`

**为什么有效**：这三条让"失败"和"正常"始终可区分。
最典型的正面案例是 **P149**：`verify consistency --from-snapshot` 在 snapshot 缺 MIG 时，
**返回 `status:"unknown"` + `verified:false` + `unknown_checks:["connection"]`**，
而不是伪造一个 pass、也不是静默跳过。这条行为后来被 P151/P156/P158.8 一路保留并补了回归。

**反例（同一时期）**：P150 我们曾用新测试替换 legacy 测试——形式上守住了"不 silent fallback"，
但**悄悄丢了契约**。纪律只覆盖了实现，没覆盖测试。

## 3. 8 个机械门禁（check_docs / check_except_pass / check_semantic_regex / check_cli_layers / gen_cli_surface --check / check_crap / check_plan / ...）

**为什么有效**：它们能挡住**形式**问题——死链、归档遗漏、未登记文档、层方向违规、
CC 超阈值、CLI 清单漂移。这些不需要人判断。

**边界（必须一起说）**：它们**全部不检查语义**。8 个门禁全绿时，
`paths --directed` 仍能把 CLOCK 当数据路径并返回 `verified`。
> **gate 全绿 ≠ 语义正确。**

## 4. worker 独立跑真实 block

**为什么有效**：P146 的 UART/I2C worker、P147 的 SPI worker、P152 的 corpus worker
挖出了主会话**结构上看不见**的问题：
- dataflow 端点污染（P146 B1）
- 无向 paths 无限运行（P146 B2）
- transitive wrapper fanin 假 contradicted（P152 N-2）
- reciprocity BIT_SELECT 误报（P152 observation）
- frontier probe 不可执行（P152 N-3）

**边界**：worker 的"独立"只是**访问独立**，不是 oracle 独立。
**主会话必须独立复现 P0**（P158 就是主会话自己跑命令复现的，不是照抄 worker）。

## 5. 真实项目优先于 fixture

**为什么有效**：真实 OpenTitan block 暴露了 fixture 永远暴露不了的问题：
`tlul_adapter_sram_racl`、`prim_packer_fifo` 这些依赖缺失、generate 层次的 BIT_SELECT 误报、
wrapper_passthrough 的 fanin 丢失、snapshot 缺 MIG 时的 connection 不可用。

**边界**：真实项目验证一度是**一次性的 worker 证据**，不是可重复 gate——
需要 corpus runner + 可加载 snapshot 才算数（P158.4 补上了 runner）。

## 6. 用户拍板"不自动识别 OpenTitan FIFO"

**为什么有效**：这是**最有价值的一次产品决策**。
把项目特定约定挡在 `core` 之外（接口可预留，样例代码放 `examples/project_adaptations/`），
避免 core 变成"某几个项目的专用工具"。P138 专门做了
`refactor(core): remove automatic FIFO inference`。

**代价**：frontier 只能给 generic boundary，`proven:false` + `evidence` + `boundary_hops`——
功能上"弱"了一些，但语义是诚实的。

## 7. 反例优先：CLOCK 对、RTL oracle、mutation 测试

**为什么有效**：把"应该**不**成立的东西"当 oracle，比"应该成立的东西"更容易发现真问题。
- CLOCK/RESET 对（`clk → ready_q` 必须 not found）比"找一个能找到的路径"更有诊断力。
- 真实 RTL oracle：P152 的 expected 手工核对到 `spi_host.sv:160`、
  `spi_host_fsm.sv:547`、`spi_host_reg_top.sv:403/418/434`。
- mutation：放宽 `DATA_EDGE_KINDS` 必须让 guard 变红。

## 8. 语义契约 + claim ledger 把"已验证"变成有状态、有证据的声明

**为什么有效**：`CLAIMS.md` 现在强制区分
`verified` / `known-broken` / `unverified` / `scoped`，
并要求每条 claim 对应一个 gate 命令。
**最有价值的一行是 C-10**：把"canonical 0 skipped 代表测试健康"**明确标成 `known-broken`**——
项目自己的历史 KPI 被自己的台账判定为 broken，这是诚实的表现。

## 9. 小步提交 + 全量门禁 + 独立复核

**为什么有效**：2026-11-11 一天内从"复盘"走到"2678 passed / 0 skipped / corpus 9/9"，
中间每个修复都是一个小 commit（P158.1~P158.8 分开提），每次都能独立验证和回滚。

**边界**：小步 + 门禁保证**没退化**，不保证**修到位**（见 G-2）。

## 10. 显式降级：exp 层 + capabilities 标注

**为什么有效**：`exp` 层有明确的降级约定（`src/cli/_registry.py:59-62`）：
无 schema 承诺、只修 bug 不加功能、默认隐藏。
`trace impact` 至今仍在 core 且 `recommended=True`（R-025），
但至少 `KNOWN_LIMITATIONS.md` §3.4 明确标了它是"**未标定的启发式**"。

# 第三部分：反模式清单

> 每条都是**可执行**的：看到就改，不要争辩。

1. **参数名叫 `output` 就 `write_text`** —— 先想"这会不会落到用户的 `.sv` 上"。
2. **`|| echo` 让门禁永远绿** —— CI 里没有 `|| true` / `|| echo`。
3. **把测试移出统计口径来让数字好看** —— 先报告失败数，再决定怎么归类。
4. **用同一实现反向生成 expected** —— expected 必须来自 RTL / 手写 oracle。
5. **只写"没有误报"的测试** —— 必须同时有"构造错误必须报"的 true-positive。
6. **用 depth 假装有界** —— 路径枚举必须有 work budget + wall-clock timeout。
7. **预算耗尽时返回 `found:false`** —— 那是"没查完"，必须 `truncated` / `unknown`。
8. **sample / truncated 的结果顶层写 `verified:true`** —— 覆盖率不完整就不是 verified。
9. **`id()` 做 key 却不持有强引用** —— 对象会被 GC，地址会被复用。
10. **用源码位置代替对象身份** —— generate 展开项共享位置，会塌缩成一个值。
11. **在三条命令里各写一份 edge 策略** —— 抽成唯一常量，让编译器/测试来防分叉。
12. **修新功能时顺手替换旧测试** —— 只新增，不替换；旧测试是契约的回归保护。
13. **把"有 worker APPROVE"当成证据** —— 要可复现命令 + 实际输出 + 反例。
14. **把一次 fresh parse 当成确定性** —— 至少 3 次重复 + canonical hash。
15. **把"corpus 文件存在"当成"corpus 被执行"** —— corpus 必须有 runner 进 gate。
16. **门禁 flag 不验证是否生效** —— `-p no:randomly` 装了插件吗？CI 跑的是 canonical 那一套吗？
17. **把"0 skipped / 0 failed"当 KPI** —— 报告要分开列 passed/failed/unknown/skipped/unexecuted。
18. **文档数字手抄** —— 计数要么自动生成，要么标"生成时间 + 生成命令"。
19. **agent 找不到的参数等于不存在** —— 每个参数都要有 discoverable 位置 + 测试。
20. **标完成时不等 worker 全部返回** —— 迟到 worker 带回来的常是 P0。

# 第四部分：如果重来一次，前 10 个决策

> 排序按"如果做对了，能省多少"。

### 1. 第 0 天就写"语义契约"，而不是第 3 天才写

如果第一天就有 `SEMANTIC_CONTRACTS.md`，A-1（CLOCK 假数据路径）、C-2（truncated verified）、
E-1（snapshot 不同构）这三类问题会**在写实现时被挡住**，而不是写完 200 个测试后才发现。
**契约要写在实现前面**（现在已写进 `DISCIPLINE.md` §0.1 第 2 条："先契约后代码"）。

### 2. 第一天就要求"测试能证明检查器本身有效"

把"关掉检查器，测试会不会红"作为**每个检查器的完成条件**，而不是事后补。
这能省掉 P-03 整轮返工，以及 P148/P150/P155 三个"修好了但没防复发"的修复。

### 3. 真实项目从第一天就用，不要留到 P146

真实 UART/I2C/SPI 暴露的问题（generate BIT_SELECT、wrapper passthrough、MIG 缺失、
filelist 依赖闭包）全是 fixture 测不出来的。把三个 block 的 filelist 固化进 repo，
能省掉"人工补 4 轮"和"外部 `/tmp` snapshot 不可复现"。

### 4. 引入 corpus runner 时就用**手写 expected**

P152 的 expected 由 CLI 反向生成，等于把实现抄成了规格。
如果第一次就手写 RTL oracle（并写行号），P158.1 改语义时**不会**出现
"T2/T7 需要重新定标"这种自我怀疑（到底是修对了还是把规格改坏了）。

### 5. 完成定义从第一天就是"代码 + 测试 + 文档 + 反事实 + 独立 oracle"

P147/P152 被提前标完成，是因为当时的完成定义只有前三项。
**完成定义是流程设计，不是最后一刻的补丁。**

### 6. 别用"worker APPROVE"当验收；主会话自己跑一遍 P0

11-11 复盘里 R-001~R-003 都是**主会话自己跑命令复现**的。
如果当时就要求主会话复现，P147/P152 的"完成"标签不会成立，
R-001（CLOCK）也不会拖到第三天才发现。

### 7. 确定性要在第一天验证，不要等有人说"byte-identical"

两次构建不一致这件事，第一天验一次的成本是 5 分钟。
我们拖到第三天，是因为一个 worker 用**一次采样**报告了"一致"。
**"deterministic" 是个需要证明的词，不是个观察。**

### 8. CI 从第一天就和本地 canonical 用同一条命令

`ruff || echo` 和 CI 测试集不一致，是**没人对账**造成的。
建 CI 的时候顺手把 canonical 命令抄过去，并对账一次。

### 9. snapshot 类需求第一天就设计成"可序列化 + 可反序列化 + parity"

E-1 的核心不是"MIG 没存"，而是**两条产生路径（live / snapshot）不同构**。
第一天画数据形状（Foundational Thinking），就不会出现 P151 那样"加一个字段"的补丁式修复。

### 10. 指标从第一天就分开报，而不是等出问题再解释

`passed / failed / unknown / truncated / unexecuted / skipped-with-reason / external-not-run`。
这一个决定能直接避免 P-01（0 skipped 掩盖 27% 失败）。

# 第五部分：对外分享版（三段式故事）

> **给不了解本项目的人听的版本。不夸大，不包装。**

### 起点

我们做了一个给 AI agent 用的 RTL 分析工具，叫 sv_query。
它能回答"这个信号从哪来""这个模块的路径怎么走""这条结论对不对"这类问题，
输出 JSON，45 个 CLI 命令，核心层只读。

2026-11-09 的时候，它的自检状态是这样的：
**2668 个测试全绿、0 失败**，还有一份 15 个任务的 agent 回归语料全过。
按常规标准，这是一个"测试覆盖率良好、可以交付"的工具。

### 转折

11 月 11 日，我们做了一次四个角度的独立复盘（架构 / 产品 / 测试 / 性能），
让四个独立的 worker 从不同角度挑毛病，**主会话再自己跑命令复现 P0**。

结果不好，但也很有价值：

- `paths --directed` 会把 **CLOCK 时钟边当成数据路径**，并且给出 `verified`。
  换句话说，工具会一本正经地"证明"一条不存在的数据通路。
- 同一份源码**连建两次图，结果不一样**（7618 vs 7620 个节点）。
- 无向路径查询在 7000 节点的图上**跑 30 秒不返回**，没有超时也没有提示。
- `verify consistency` 只检查了 32 项、跳过了 168 项，**顶层仍然写 `verified: true`**。
- `filelist prune --output` 会**直接覆盖用户的 `.sv` 文件**。
- SPI 项目的 9 个任务语料**只有 JSON 文件，没有任何程序会执行它**。

最刺痛的一条，是我们自己在前一天的记录：

> 2026-11-10，P152 完成，worker 判定 "APPROVE WITH NITS，9 tasks / 16 assertions 全过"。
> 2026-11-11 发现，这 9 个 task 根本没有 runner。

还有一条更该说的：前一天的 P157 我们把 12 个 skip 清理掉，canonical 变成 **"0 skipped"**，
并当作成果写进了文档。我今天重新跑了一遍那批被移出去的测试：
**141 个里 38 个失败，约 27%**。
"0 skipped" 不是质量提升，是**把失败移出了统计口径**。

我们自己的评审文档写得很准：

> 这次不是"规则不够多"，而是**规则检查的是形状，产品承诺的是语义**。

8 个机械门禁全绿的时候，工具仍然会在时钟边上说谎——
因为没有任何一个门禁会问"这条边**是不是数据边**"。

### 现在

11 月 11 日当天我们做了 P158 这一轮修复，把"词"变成"契约"：

- **数据边唯一化**：新增 `contracts.py`，所有命令引用同一组常量；
  `clk → ready_q` 现在返回 `found:false` / `contradicted` / `is_reachable:false`，
  而真实数据路径仍然正常通过。
- **有界搜索**：路径枚举加 work budget + wall-clock timeout。
  同样那条 SPI 查询从"30 秒无返回"变成 **0.6 秒**并显式返回 `truncated` + 原因。
- **确定性**：根因是 `id(pyslang wrapper)` 遇到 GC 地址复用。
  中间试过"改用源码位置"——**失败了**（generate 展开项共享位置，18 个测试挂掉，方案回退）。
  最终解法是保留 `id()` 语义但**持有强引用**保活对象，连续多次构建结果一致。
- **诚实的状态机**：sample / truncated 不再能拿到顶层 `verified: true`。
- **可执行的语料**：SPI corpus 有了 runner，9 个任务真的会跑，错误 expected 会失败。
- **写入安全**：默认 dry-run，`--apply` 才写，只允许 `.f/.fl`，覆盖要先备份。
- **claim 台账**：我们自己把"canonical 0 skipped 代表测试健康"登记为 **`known-broken`**。

当前状态：`2678 passed / 0 skipped / 131 deselected`，SPI corpus 9/9。
但**这个"0 skipped"现在有了不同含义**——它是 141 个外部依赖测试被明确移出后的数字，
不是"全部健康"。

我们也在项目文档里留了一行诚实的话：

> 强原型，不是已完成的客观验证层。

**还没做完的**（P158.7 / P158.9~P158.12）：
snapshot 的 live/snapshot 同构、snapshot surface 能力矩阵、CI 与 canonical 咬合、
snapshot 损坏输入的健壮性、以及那 27% 的外部测试——它们还在失败，还在门外。

**这段故事想说的只有一件事**：
> 如果你的工具的输出被用来做决策，那么"测试全绿"和"结论可信"之间，
> 需要的是**可反证的门禁**，而不是更多的测试。
