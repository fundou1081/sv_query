## Findings

### F1 — P1 (NEW, introduced by this commit): cross-module array-element driver silently lost

- **file:line**: `src/sv_query/trace/core/graph_builder.py:1488-1493` (`_mark_array_base` now writes `node.width` / `is_signed`) reached via `:1495-1500` `_mark_unpacked_arrays` in the early pipeline stage `graph_builder.py:113` (`array_elements`, before `bus_bit_bridges` / `bit_bridge_synth`). P197.22 only set `extra["is_array"]`.
- **Repro (minimal legal RTL)**:
  ```
  module sub(output logic [31:0] o [0:3]); assign o[0] = 32'h1; endmodule
  module top(output logic [31:0] mem [0:3]); sub u(.o(mem)); endmodule
  ```
  - Parent `ded979a4`: `trace top.mem[0]` → **1 driver `1'b1`, high**; graph `14 nodes / 9 edges`; edge `top.u.o[0] → top.mem[0]` (CONNECTION) present.
  - HEAD `586bc4fd`: `trace top.mem[0]` → **0 drivers, uncertain**; graph `7 nodes / 5 edges`; edge absent. `trace top.u.o` → 0 drivers (parent: 1).
  - CLI, user-facing, `--no-cache`: parent `drivers 'top.mem[0]' --json` → `count=1`, `precision="bit"`; HEAD → `count=0`, `precision="unknown"`, `resolution="bit_base_fallback"`.
  - Also on the existing P197.22 fixture (`sub u(.o(mem))`, top `assign mem[0]=a`): parent `top.mem[0]` drivers `['top.a', "1'b1"]`, HEAD `['top.a']` — submodule driver lost.
- **Isolation**: monkeypatching `_mark_array_base` on HEAD to only set `is_array` restores the edge and the driver (`15/9 → 15/9` with driver present); disabling `_fix_instance_array_metadata` does not. Root cause is early width mutation on type-level array nodes, **not** the instance-id lookup.
- **Impact**: silent wrong answer / false "nothing drives this bit" — same severity class as prior P1 finding `docs/validation/reviews/2026-11-26_5c5e9d8.md`. The green 3369-test gate did not catch it: only `top.mem[9]` is asserted in the relevant test.
- **Fix direction**: do not mutate `node.width` on type-level (`module.var`) nodes during the early pipeline stage; collect array symbol widths once and apply type-level + instance-level metadata **after** MIG/bit-bridge stages (or make `_mark_array_base` metadata-only for the early pass and backfill widths only on instance-qualified nodes post-MIG). Verify the lost driver is restored, then re-run the full gate.
- **Test gap**: add a positive assertion to the P197.22 driven-array fixture, e.g. `trace_detailed("top.mem[0]").drivers` contains the submodule literal/driver, so the regression fails on a reverted tree.

### F2 — P2 (cache key closure / stale state): fix silently inert on warm caches

- **file:line**: `src/sv_query/trace/core/cache/ast_cache.py:64` `CACHE_VERSION="3.5"` and `build_identity.py:15` `GRAPH_SEMANTICS_VERSION="1"` unchanged; `BuildIdentity.key()` does not include code semantics. CLI builds with cache on by default (`use_cache=not no_cache`).
- **Repro**: isolated parent tree builds fixture with `use_cache=True` into a temp `SVQ_CACHE_DIR` (writes `width (3,0)`, `is_array=None`); HEAD with identical source and `use_cache=True` reports `cache_status=hit`, `width (3,0)`, `is_array=None`. Cross-direction contamination also observed: HEAD-written cache made the parent CLI return the same (wrong) empty-driver result.
- **Fix**: bump cache schema / `GRAPH_SEMANTICS_VERSION` for this graph-semantics change (P197.21 precedent) or include a graph-semantics fingerprint in the key; add a cache-hit test asserting instance array metadata. Latent until an upgrade with a warm cache, hence P2 — but user-visible on the default CLI path.

### F3 — P2 (claim accuracy / duplicate scan): symbols scanned 3× per build

- **file:line**: `graph_builder.py:1496`, `:1504`, `:1526`. Instrumented call stack:
  ```
  SCAN_CALL _fix_array_element_widths -> _mark_unpacked_arrays
  SCAN_CALL _fix_instance_array_metadata
  SCAN_CALL _fix_instance_array_metadata -> _fix_array_element_widths -> _mark_unpacked_arrays
  ```
  (`get_modules()` called 9 times in that build.) Pure/repeatable, so no direct wrong answer, but the commit message "scan semantic array symbols once" is not satisfied, and duplicate application across pipeline phases is what enables F1.
- **Fix**: memoize `self._array_symbols` on the builder; apply widths once, after MIG construction, to both type-level and instance-qualified nodes.

## What is correct (avoid false positives)

- Semantic AST (pyslang `isUnpackedArray` / `elementType` / `bitWidth` / `isSigned`) is used throughout; no source-regex or node-name guessing.
- Instance ids come from MIG (`inst.id`, e.g. `top.u1`), `module_type` from the adapter — not a hand-built prefix. MIG itself is unmodified (identical `to_dict()` digest) and its build order after graph build is correct.
- `is_array` guard for packed-bit vs array-index provenance stays in one place; no new synthetic driver or `verified` claim is emitted for a missing element.
- Width `(31,0)` is element width (`logic [31:0]`), correctly replacing the parent's mistaken unpacked-range width `(3,0)` on instance nodes.
- Instance-element `array_element` / `parent` metadata is applied after MIG via `_fix_array_element_widths()`, and that pass is idempotent (`setdefault`).
- `hasattr(self, "_graph_builder")` hook is safe on fresh builds; cache hydration does not call it, but hydrated graphs carry serialized metadata (see F2).
- Full gate, docs counts, privacy, and prior-fix (P197.21/22) tests remain green; no unrelated regression was found outside F1.
