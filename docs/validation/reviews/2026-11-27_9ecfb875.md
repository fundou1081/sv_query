## 3. Findings

### P0 — none.

### P1-1 — JSON quiet contract broken by connection_extractor warnings on filelist projects

**Repro (exact):**
```bash
S=/tmp/svq-pypi-smoke/bin/sv_query
$S stats --filelist /tmp/serv.f --json >/tmp/o 2>/tmp/e; echo $?; wc -c /tmp/e; wc -l /tmp/e
# rc=0; stderr = 24360 bytes, 216 lines (stdout 744 bytes, ok=true)
$S stats --filelist /tmp/serv.f --json --quiet 2>/tmp/e2; wc -c /tmp/e2   # 24360 — not suppressed
$S stats --filelist /tmp/serv.f --json --verbose 2>/tmp/e3; wc -c /tmp/e3  # 25524 — worse
```
Sample stderr: `[connection_extractor] port 'i_clk' not in module_ports for serv_csr; falling back to PORT_IN (likely ref port or missing module def)` and `port 'o_q' width missing for serv_csr; falling back to (1,0)`, repeated for 27 ports × 4 instances.
Also reproducible with `graph nodes`, `ports`, `connections` on the same filelist; single-file picorv32 is quiet.

**Impact/why P1:** CLI advertises `--verbose` = "Keep stderr diagnostics in JSON mode (default: JSON is quiet)" and core layer promises JSON + quiet; an agent's JSON consumer now gets 24 KB of unstructured log on stderr. `--quiet` is ignored for these messages.
**Root cause (read-only inspection):** `src/sv_query/trace/core/connection_extractor.py:381-401` calls `logger.warning(...)` directly, bypassing the CLI quiet adapter. Same in repo HEAD.
**Fix direction:** route as structured entries into the JSON envelope (`errors`/new `warnings` field) or gate on the active quiet flag; never raw logger → stderr in `--json` default mode.

### P1-2 — Graph misclassifies ports of a generate-scoped parameterized instance (`serv_csr`)

**Repro (exact):**
```bash
S=/tmp/svq-pypi-smoke/bin/sv_query; F=/tmp/serv.f
$S ports serv_rf_top.cpu.gen_csr.csr --filelist $F --json
# by_direction = {"input": 27}; o_q / o_csr_in / o_new_irq direction=input, width=[1,0]
$S connections serv_rf_top.cpu.gen_csr.csr --filelist $F --json
# port_count=28; o_q / o_csr_in / o_new_irq direction=output
$S graph nodes --filelist $F --match csr.o_q --json
# kind=PORT_IN (both serv_rf_top and serv_synth_wrapper instances)
$S drivers serv_rf_top.cpu.gen_csr.csr.o_q --filelist $F --json   # 23 drivers, 0 loads
$S loads   serv_rf_top.cpu.gen_csr.csr.o_q --filelist $F --json   # 0 loads
```
**Ground truth:** `serv/rtl/serv_csr.v:15-45` declares `o_new_irq`, `o_csr_in`, `o_q` as outputs and
`i_rf_csr_out/o_csr_in/i_csr_imm/i_rs1/o_q` as `[B:0]` (`B = W-1`, instance overrides `W`).
The MIG-based `connections`/`instances` get directions right, so the graph degradation is internal, not a source/filelist defect.

**Impact/why P1:** real, mainstream RISC-V core. Output ports become input nodes and parameterized
widths collapse to 1 bit in the semantic graph used by `drivers`/`loads`/`paths`/bit queries; agents
reasoning on `o_q`/`i_rs1` get wrong direction and wrong width. Also explains the P1-1 warnings.
**Root cause:** `connection_extractor.py:378-408`: when the module name is absent from `module_ports`,
`_port_extra` returns `{"direction":"missing","fallback":"PORT_IN"}` and `_port_width` falls back
to `(1,0)`. Generate-scoped parameterized instance name lookup fails. Present in repo HEAD.
**Fix direction:** resolve instance definition to the elaborated definition (`inst.definition`)
rather than a raw type/name key, and inherit effective parameter widths from the MIG; add a regression on SERV `gen_csr.csr`.

### P1-3 — Evidence for internal driven signals is unusable, and can be falsely "verified"

**Repro A (false positive):**
```bash
S=/tmp/svq-pypi-smoke/bin/sv_query; P=/Users/fundou/my_dv_proj/openrtl/picorv32/picorv32.v
$S trace evidence picorv32_axi.picorv32_core.trap --file $P --json
# source_location.line_start = 1189
# source_text = 'if (cpu_state == cpu_state_trap)   dbg_ascii_state = "trap";'
# enclosing_if line 1188; enclosing_always = null; is_verified = true; credibility_score = 0.4
sed -n '1403p;1488p' $P   # 'trap <= 0;' and 'trap <= 1;'  <-- real drivers
grep -n '"trap"' $P | head  # line 1188 is a debug string literal, not the signal
$S drivers picorv32_axi.picorv32_core.trap --file $P --json --evidence
# driver evidence file=picorv32.v line=1189 for both drivers — same wrong location
```
The reported location is a debug `always @*` block whose only `trap` token is the **string literal**
`"trap"`. `Evidence.is_verified` (`src/sv_query/trace/core/trace_evidence.py:108-124`) is
`snippet_present AND (matches_source_expr OR matches_signal_name)`; `signal_token_present`
(`source_assignment.py:59-64`) regex-matches the leaf name with word boundaries, so `"trap"` scores
as a match. Result: `is_verified=true` for evidence that does not contain the driver at all — a
direct violation of the query protocol rule "do not write unknown/partial as verified".

**Repro B (false negative):**
```bash
$S trace evidence picorv32_axi.picorv32_core.instr_trap --file $P --json
# source_location=null, source_text="", is_verified=false, score=0.0
# yet RTL line 679: assign instr_trap = (CATCH_ILLINSN || WITH_PCPI) && !{...};
$S trace evidence serv_rf_top.cpu.gen_csr.csr.mcause --filelist /tmp/serv.f --json
# same empty evidence for an internally driven REG
```
**Impact/why P1:** evidence is the substrate for `verify claim`; wrong location + false verified flag
can make an agent "prove" a claim from an unrelated string literal. Silent empty evidence on real
internal wires makes the tool unusable for the advertised internal-signal evidence workflow.
**Fix direction:** bind `source_location`/`source_text` to the driver edge's semantic syntax node
(not text search near a hint); require LHS-token + RHS-expression check against the *driver* snippet,
exclude string literals/comments; return an explicit `error`/`resolution` rather than silent empty
evidence when no driver syntax can be resolved. Present in repo HEAD.

### P2 (non-blocking caveats)

- **P2-1 Session seam inconsistency**: `capabilities` works via `session --request` but returns
  `E_UNSUPPORTED_OP` via `session --serve --file …`; `--serve` without `--file` rejects even
  `version` with `E_INVALID_REQUEST`. `graph_nodes` op unsupported in both (documented D15 seam).
- **P2-2 Evidence payload bloat**: one `trace evidence` response = 164,613 B; `enclosing_chain`
  embeds the entire 69,203-char `module picorv32` source. Agent JSON consumers risk context blowup;
  consider capping chain snippets.
- **P2-3 `trace profile … .trap` reports `driver_count=3`** because a CLOCK edge is counted,
  whereas `drivers` default=2 and `--include-clock`=3. Not a data-edge claim, but agents must not
  read profile count as data drivers (AGENTS.md rule 13).
- **P2-4 Truncation markers on tiny-looking results**: driver CONST `1` shows
  `condition_truncated=true` with one visible condition path because the global CONST node id `1`
  explodes path enumeration to the 5000-expansion cap. Legitimate, but don't claim full condition
  coverage from a single-path view.
- **P2-5 Environment**: CVA6 unusable here (missing absolute top path + incomplete submodules);
  not a tool bug.
- **P2-6 Dev-only**: `importlib.metadata.version('sv_query')` from the repo checkout is `0.3.2`
  (stale egg-info) while `pyproject.toml`/wheel/session report 0.3.7; harmless local artifact.

   on SERV `gen_csr.csr` and picorv32 `trap`/`instr_trap`.

   `ports`/`connections`/`graph nodes` agree on direction for the SERV CSR instance.

4. Until the patch ships, consumers should: pipe `2>/dev/null` for filelist JSON, treat `ports`
   directions/widths on parameterized generate instances as untrusted (prefer `connections`), and
   ignore `trace evidence.is_verified` for internal signals — confirm with `verify claim` instead.
