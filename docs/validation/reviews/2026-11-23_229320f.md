### P2-1 — residual CLI/session path-claim divergence for bit-select nodes resolved via `bit_base_fallback`
File: `src/sv_query/trace/core/query/verification.py:100-116` and `:46-52`; injected resolvers `src/sv_query/cli/core/semantic/verify.py:78-85` (`_cli_resolve`) vs `src/sv_query/trace/core/query/session_ops.py:13-26` (`_resolve`/`_session_resolve`).
Repro (bus design `module top(input logic [7:0] a, output logic [7:0] y); assign y=a; endmodule`):
- claim `{"type":"path","from":"top.a","to":"top.y","nodes":["top.a[0]","top.y[0]"]}` → CLI `contradicted` ("path endpoints do not match from/to"), session `unknown` ("path node 'top.a[0]' None").
- claim with `from="top.a[0]"` → CLI `contradicted` ("claimed path edges missing"), session `unknown` ("endpoint unresolved").
Cause: CLI `resolve_signal` returns `ok=True, status="bit_base_fallback", resolved=<synthetic bit id>` (`trace_common.py:460-462`), while session `_resolve` returns `( "", None )` for the same string. The verdict *logic* is shared; the injected *resolution policy* is not (by design: module docstring "Resolution policy is injected by the caller"). Both outcomes are conservative (neither is `verified`), so this is parity debt, not a wrong answer. Pre-existing in parent; not introduced here.
Fix: either give session a comparable bit-base fallback resolver, or normalize `bit_base_fallback` to a single shared `unknown` before endpoint/edge checks.
Test gap: no test exercises bit-select endpoints in a path claim on either side.

### P2-2 — endpoint-match branch is not uniquely guarded by a reverted-fix test
File: `sim/tests/unit/test_p197_2_verify_parity.py:29-36` (`test_path_claim_verdict_matches_cli`) and shared `_explicit_path` `verification.py:46-51`.
The chosen claim `nodes=["top.a","top.y","top.a"]` triggers the endpoint-mismatch branch, but on the parent commit the session also returned `contradicted` via the missing `top.y→top.a` edge, so this test passes on parent and would not fail if the endpoint check were deleted. The bidirectional parity test (`:39-49`) *is* a valid revert test (parent session returned `verified`), so the P197.2 fix as a whole is guarded — only the endpoint sub-check is not.
Fix: add a case with no checkable edge, e.g. `{"type":"path","from":"top.a","to":"top.y","nodes":["top.a"]}` — with the check it is `contradicted`, without it would be `verified` (parent session behavior confirmed empirically).
Test gap: as above.

### P2-3 — session unknown envelope shape changed from flat `unknown_kind` to `machine`

### P2-4 — `port_node_missing` violation has no direct test
File: `verification.py:193-205` (now used by both CLI `_check_connections` at `verify.py:341-342` and session `_connection_check` at `session_ops.py:41-42`).
Grep over `sim/tests` finds zero references to `port_node_missing`. The commit message claims "connection includes port_node_missing", but no gate asserts that violation kind on either path. Practical risk is low: in the normal semantic path `internal = f"{inst}.{port}"` equals `port_id` (`module_instance_graph.py:208-221`), so the branch is only reachable via legacy/mutated snapshots — exactly the scenario the prior review reproduced for `internal_missing`. No in-repo regression observed.
Fix: add a snapshot-mutation test that sets `internal_signal` to an existing node while omitting `<inst>.<port>`, asserting the violation on both CLI and session.
