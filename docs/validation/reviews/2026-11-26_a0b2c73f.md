## Verification against the six requested items

### 1. Ascending slice `y[2:5]` on `[0:7]` preserves dependencies — PASS

`module top(input logic [7:0] a, output logic [0:7] y); assign y[2:5] = a << 2;`

| query | rel 0 (`y[2]`) | rel 1 (`y[3]`) | rel 2 (`y[4]`) | rel 3 (`y[5]`) |
|---|---|---|---|---|
| `_expr_source_bits(slice, r)` | `top.a[1]` | `top.a[0]` | `[]` | `[]` |
| CLI `trace fanin` | `top.a` | `top.a` | `[]` | `[]` |

IR: `Cast w=4(ShiftLeft w=8(a,2))`; IR offsets 0/1 are shift zero-fill, 2=`a[0]`,
3=`a[1]`. Parent `y[0:7]` is ascending, so `_dst_ir_bit` maps `want_bit r → 3-r`
— correct, and still intact after the `a0b2c73f` change. No fabricated source.

### 2. Descending slice `y[5:2]` on `[7:0]` — PASS (prior P1 fixed)

`module top(input logic [7:0] a, output logic [7:0] y); assign y[5:2] = a << 2;`

| query | `y[2]` | `y[3]` | `y[4]` | `y[5]` |
|---|---|---|---|---|
| `_expr_source_bits(slice, r)` | `[]` | `[]` | `top.a[0]` | `top.a[1]` |
| public CLI `trace fanin` drivers | `[]` | `[]` | `top.a` | `top.a` |

- y2/y3 are genuine shift zero-fill: **no `a` source**, no fabricated source.
- y4/y5 depend on `a`; **public CLI is non-empty** for the driven bits.
- Mechanism confirmed by metadata dump: slice node `width=(5,2)`,
  `parent_bit_start=2`, `parent_bit_end=5` (normalized/ascending), **parent
  node `width=(7,0)`**, `_slice_is_ascending=False`, so `_dst_ir_bit` returns
  `want_bit` (identity) instead of `width-1-want_bit`. This is exactly the
  `9057ba70` root cause, now corrected at the declared parent.
- Ground truth: SV semantics of a 4-bit truncation of `a << 2` give
  `y[5]=a[1]`, `y[4]=a[0]`, `y[3]=y[2]=0`; an independent SV-model probe
  (`/tmp/p19713_ra_slice_matrix.py`) matches the tool on all 4 bits, and the
  archived Verilator 5.048 run in the prior re-audit gives the same values.
  (A fresh Verilator rebuild this session was blocked by a local C++ toolchain
  `'cstdint' not found` error — an environment issue, not a product finding.)
- All five shift ops (`<<`, `>>`, `<<<`, `>>>`, `$signed(a) >>>`) were re-run on
  both legal slice directions; descending results are `[[],[],a[0],a[1]]` for
  left shifts and `[a[2],a[3],a[4],a[5]]` for right shifts — consistently
  correct, no reversed mapping.
