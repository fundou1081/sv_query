## Findings

### P1-1 (prior audit) — FIXED, re-audited on 4 surfaces

`src/sv_query/trace/core/assignment_source.py:13-26` now reads `compiler.timescale_injected` (exact-key lookup, then basename fallback) and subtracts 1 **only** when that map says the tracer actually injected a timescale. The `startswith("`timescale")` + `is_file()` guess was removed. `src/sv_query/trace/unified_tracer.py:304-322` records the map by comparing the raw source dict captured before `preprocess_all()` with the post-preprocess text (`"`timescale" not in before[:500] and "`timescale" in after[:500]`), then copies it onto the compiler at `_get_compiler()`.

Verified matrix (target vs parent):

| Input | Parent | Target | Expected |
|---|---|---|---|
| Inline `sources` explicit timescale | 2 | **3** | 3 |
| Inline `sources` no timescale (injected) | 2 | 2 | 2 |
| Bare-basename filelist, explicit timescale (fifo.sv) | 32/33 | **33/34** | 33/34 |
| `files=[abs_path]`, explicit timescale | 2 | **3** | 3 |
| `files=[abs_path]`, no timescale | 2 | 2 | 2 |
| picorv32 filelist (injected via original text) | 1488 | 1488 | 1488 |

No false-injection path found: `preprocess_macros()` excludes macro values starting with a backtick from its resolved table, and `auto_inject_package_imports()` cannot synthesize a `` `timescale `` line, so the before/after comparison cannot report injection that never happened. `inject_default_timescale()` injects exactly one line, matching the unconditional `-1`. Direct `SVCompiler(sources=...)` use does not inject timescale itself, so the retained `compiled_line_shift()` disk-comparison fallback is appropriate there.

### P2-1 — Snapshot test still only asserts non-empty `source_text` (carried over, partially mitigated)

`sim/tests/cli/test_trace_snapshot.py:160-170` still asserts `ev.get("source_text")` truthy but not the exact line. The two new unit tests now cover exact lines under timescale, so the P1 scenario is covered; the snapshot assertion alone would not catch a line regression. Re-audit probe confirmed the actual snapshot line is correct (33).

### P2-2 — Continuous DRIVER edges from net declarations have no provenance (carried over, unchanged)

On target, picorv32 still has **490/715** continuous DRIVER edges with `source_location=None` (e.g. `dbg_mem_valid`, `mem_la_firstword`). `assign_extractor.create_assign_edges()` handles `ContinuousAssignSymbol` only; `wire x = y;` initializers route through `net_decl_extractor`, which never calls `_assignment_location()`. Unconditioned, so not directly C-78; not introduced by this fix.

### P2-3 — Debug-only fallbacks on semantic-location failures (carried over, unchanged)

`assign_extractor._assignment_location()` returns `None` on any exception; `always_extractor.py:841-849` logs only at debug level. The `driver_extractor.py` post-pass can then write a *condition* line, conflicting with iron rules 2/3. No occurrence observed in probed projects.

### P2-4 — Cache identity not bumped; warm cache silently preserves the pre-fix wrong line (carried over, now demonstrated)

`BuildIdentity.GRAPH_SEMANTICS_VERSION` stays `"2"` and `PACKAGE_VERSION` stays `"0.3.8"` across `fd5b2ccd → 51635691 → 6f38a802`. Reproduction (separate processes, shared `SVQ_CACHE_DIR`):

```
parent   build_graph(use_cache=True)  -> cache_status=miss key=8d6caf2ad666d40a line=2   (wrong)
target   build_graph(use_cache=True)  -> cache_status=hit  key=8d6caf2ad666d40a line=2   (stale!)
target   build_graph(use_cache=False) -> cache_status=disabled                 line=3   (fixed)
```

CLI `drivers --evidence` uses the cache by default (`use_cache=not no_cache` in `cli/core/semantic/trace.py`), so an existing pre-fix cache entry keeps returning the wrong line after upgrading to this HEAD. Fresh builds are correct. Not introduced by this commit (the same gap was P2-4 in the prior audit, and the project bumps package version at release), so it does not block closing the P1, but it must be addressed before any release (bump `GRAPH_SEMANTICS_VERSION` or ship a version bump).

### P2-5 — Pre-existing CLOCK/RESET location pollution (carried over, unchanged)

`driver_extractor.py:1358-1374` still fills `source_location` from `condition_ast` for any edge lacking one, including CLOCK/RESET edges (target *and* parent). `edge_factory.py` itself correctly clears non-DRIVER locations, so this commit adds none.

### Latent design note (not a finding)

`edge_factory._CURRENT_ASSIGNMENT` is a module-global ContextVar set in `always_extractor.py` and never reset with a `token.reset()` in `try/finally`. No stale-location leak was observed in the probed builds, but the global is fragile for long-lived sessions. Unchanged from prior audit.
