### C2 — P2 — width filter uses `bitWidth` (bit count) against absolute select indices
**Location**: `src/sv_query/trace/core/extractors/_common.py:523-528, 626-630`.
`_base_symbol_width` returns `node.value.type.bitWidth` — a **count** of bits. The filter compares `max(msb,lsb) >= base_width`. For a signal declared with a non-zero lower bound, select indices are absolute (`data[5:4]` on `wire [7:4] data`), so the comparison is invalid.
**Repro** (read-only, in-memory):
```verilog
module top(input logic [7:4] data, output logic [1:0] y);
  assign y = data[5:4];   // valid select
endmodule
```
With filter ON: `top.data[5:4]` exists but `parent=None`, `bit_range=None`, no BIT_SELECT edge. Monkeypatching `_base_symbol_width = lambda n: None` restores `parent=top.data`, `bit_range=[5:4]`, width `(5,4)`, and edge `top.data[5:4] → top.data`. Same for OOB `data[8:7]`: filter removes the range node's metadata; the OOB is still reported via `top.data[8]`, so no false verified.
**Impact**: silent loss of BIT_SELECT edges / parent metadata for valid `[M:N]` selects (common in RTL). Outcome-level verification is not corrupted (bit-expanded nodes still carry OOB), hence P2 not P1.
**Fix**: compare against the elaborated type's upper bound (e.g. `type.range.left/right` max) rather than `bitWidth`, or only filter when the base type's declared range starts at 0. Keep the active-OOB case reportable.
**Test gap**: no test covers a `[7:4]`-style parent with a RangeSelect; add one asserting the BIT_SELECT edge and `parent_bit_start/end`.

### C3 — P2 — width filter drops active OOB RangeSelect walker hit (acceptance-item nuance)
**Location**: `_common.py:626-630`.
The comment ("a select beyond the elaborated base width cannot be active") is semantically wrong for SystemVerilog: an OOB part-select is legal and active (out-of-range bits are X). The filter therefore skips active OOB selects such as `data[3:0]` on 2-bit `data` (repro: `iter_bit_selects` → `[]`). Acceptance item 3 still passes because bit-expansion reports bits 2/3 and the checker returns `fail`; in non-driver contexts the select disappears and the check returns `unknown` (honest, not `verified`). This is a coverage/architecture debt, not a false verified.
**Fix / test gap**: if walker completeness is a goal, restrict the filter to genuinely inactive generate branches (use pyslang's generate-branch activity, not width), or accept and document the bit-expansion dependency. Add a regression that asserts OOB is reported for a RangeSelect in a context with no bit-expansion.
