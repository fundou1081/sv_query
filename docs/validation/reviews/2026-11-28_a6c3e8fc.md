## 2. Findings

### R1 — Connection-follow is not applied on the `--from-snapshot` path (P2, scope gap; pre-existing)

- Location: `src/sv_query/cli/core/semantic/trace_evidence.py:105-145` (`_snapshot_edge_evidence`)
  and `src/sv_query/cli/_evidence_helpers.py:44-53` (`_NullAdapter` for snapshots).
- Repro: `run_cli.py snapshot save /tmp/mod_out.sv --tag audit`, then
  `run_cli.py trace evidence top.y --from-snapshot audit --json` → `source_location=null`,
  `source_text=""`, `is_verified=false`, even on target HEAD. Direct-file mode gives line 2/true.
- Cause: snapshot fallback scans only *direct* incoming edges that carry `source_location`;
  the `top.u.q → top.y` CONNECTION edge has none, and the resolver is built with a `_NullAdapter`
  so the new step 1b cannot reach semantic snippets. The new code lives in `resolve()`, which
  this path bypasses.
- Parent behaves the same (empty `top.y` from snapshot), so this is **not a regression**; it is a
  scope hole relative to the item goal ("module-output evidence returns empty").
- Fix: extend `_snapshot_edge_evidence` to hop CONNECTION edges to the source port before
  selecting a located driver edge, or give the snapshot resolver a source-backed adapter.
- Test gap: new test covers only `-f ... --no-cache`, not `--from-snapshot`.
- Severity P2 (explicit unknown, never false verified; no data loss).

### R2 — Connected top output carries `signal=top.y` but snippet text references `q` (P2, precision caveat)

- Location: `trace_evidence.py:249-253` (`source_ev.signal = signal_id`).
- Evidence for `top.y` has `matches_signal_name=false` (leaf `y` not in `q <= d;` snippet) and
  `is_verified=true` only via `matches_source_expr` (`d` present); score 0.6 vs 1.0 for `top.u.q`.
- This is semantically acceptable (the assignment genuinely drives `y` through the port), but a
  consumer that equates score 1.0 with verification may misread it. Not a false verified.
- Fix idea: record the traverses connection path / annotate aliasing rather than silently
  renaming `signal`. Low priority.

### R3 — `line_is_lhs` regex limitations (P2, edge cases; no false positives found)

- Location: `source_assignment.py:87-92`, new group `(?:@\s*\([^)]*\)\s*)?`.
- False negative repro: `line_is_lhs("always_ff @(posedge clk iff (en)) q <= d;", "q")` → `False`
  because `[^)]*` stops at the first `)` of the nested condition. Also
  `_source_line_from_file()` (`trace_evidence.py:213-224`) copies the raw line without stripping
  `//` comments and without `compiled_line_shift`, unlike the step-7 fallback; direct resolver
  consumers may see `q <= d; // comment`. CLI post-processing masks this.
- Fix: balanced-paren scan for event control; route the new fallback through
  `find_assignment_near`/`strip_block_comments`. Low priority.
