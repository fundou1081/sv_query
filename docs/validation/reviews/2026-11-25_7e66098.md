## 2. Findings

### F-10C-P2-1 — Bit-query authority is depth-dependent; `depth=1` still returns the duplicate aggregate
Severity: **P2** (borderline P1 if the "bit query -> bit drivers" rule is declared depth-independent)

Location: `src/sv_query/trace/core/query/signal.py:1077-1093` (fix applied only here)
vs `src/sv_query/trace/core/query/signal.py:1301-1390`, specifically the second parent
driver mapping at `:1354-1372` inside `_find_drivers` (no equivalent suppression).

Repro (user-facing CLI, fixture written outside the repo):
```
python3 run_cli.py drivers 'top.y0[0]' -f asc_ps.sv --json --pretty
  -> drivers: [ top.a[5] ]                       # correct

python3 run_cli.py drivers 'top.y0[0]' -f asc_ps.sv --depth 1 --json --pretty
  -> drivers: [ top.a[5], top.a[2:5] ]           # duplicate aggregate survives
```
Same at the Python API: `trace_fanin('top.y0[0]', depth=1)` returns
`{top.a[5], top.a[2:5]}`; default depth returns `{top.a[5]}`.

Root cause: `trace_fanin(depth=1)` routes to `_find_drivers`, which maps parent bus
drivers through its own loop and never consults the P198.10c suppression. Only the
recursive `_trace_drivers_recursive -> _trace_parent_bit_drivers` path was patched.
`--depth/-d` is a documented, exposed CLI option, so this is reachable normally.

Impact: the commit message and `docs/validation/P19810_PART_SELECT_2026-11-25.md`
state an unqualified authority rule ("bit query -> bit drivers, bus query -> bus
aggregate"). At `depth=1` the answer silently carries an extra coarse driver — the
exact behavior this change claims to remove. Fanout, `paths --bits`, and bus-level
`dataflow analyze` were probed and are consistent; fanin depth=1 is the outlier.

Test gap: the new test uses default depth only. There is no depth=1 part-select
authority test anywhere in `sim/tests/` (grep confirmed). A green 3307-test gate does
not cover this path.

Required rework (not performed here, read-only): apply the same bit-authority check in
`_find_drivers`'s parent-driver loop, or better, centralize the "bit query -> bit
drivers" decision in one helper used by both sites; add a depth=1 regression test
asserting `fanin(y0[0], depth=1) == {a[5]}` and a bus-depth-1 test asserting
`fanin(y0, depth=1) == {a[2:5]}`.

### F-10C-P2-2 (caveat, not a reproduced failure) — authority check is an id-string heuristic
`any("[" in psrc and ":" in psrc for psrc, _ in parent_sources)` decides "part-select
aggregate" from node-id text, and checks the *parent* source rather than whether the
queried bit actually has a precise direct part-select driver. The comment in the code
claims the latter. I probed mixed multi-driver variants
(`assign y=a[0:3]; assign y[3]=1'b1` and `assign y=a[2:5]; assign y0[0]=1'b1`) and did
**not** find a wrong answer — the precise bit edge already carries the correct driver
in each case. Still, the test is coupled to id spelling and to the graph builder
always emitting bit edges; it should be expressed against graph metadata (e.g. edge
`sources`/slice nodes) before being treated as a durable contract. Track as latent
debt, not a blocker.

### Out-of-scope residual (records why P198.10 cannot close)
`assign {y1,y0} = {a[1:4]};` (reversed/invalid select) still yields **no edges, no
unknown, empty fanin** — P198.10a ("surface invalid select as explicit
`invalid_part_select` unknown, no silent skip") is untouched by this change. The
investigation doc already lists this as required split item 1.
