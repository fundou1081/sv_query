### P2-1 — precision contract not universal for relative-form queries (edge / consistency debt)

- **file:line**: `src/sv_query/cli/core/semantic/trace.py:496` (`query_precision(sig, list(items), graph)`), `src/sv_query/cli/core/semantic/trace_common.py:285` (`node = graph.get_node(signal) ...`).
- **Root cause**: `_trace_one_row` passes the **raw user string** `sig` to `query_precision`, while the traced items come from the resolved id `query_sig` (`trace.py:586,599`). `resolve_signal` accepts relative forms; `graph.get_node("mem[0]")` misses even though `res["resolved"] == "top.mem[0]"` exists with `array_element=True`, so the new early return does not fire.
- **Repro** (HEAD, fixture `module top(input logic [31:0] a, output logic [31:0] mem [0:3]); assign mem[0]=a;`):
  - `drivers 'top.mem[0]' ... --json --no-cache` → `resolution=exact`, `precision=bus`, `coarse_fallback=false`, `count=1`, driver `top.a`. ✓
  - `drivers 'mem[0]' ... --json --no-cache` → `resolution=relative`, `resolved_signal=top.mem[0]`, **`precision=bus`, `coarse_fallback=true`**, `count=1`, driver `top.a`. — contradicts the new doc line "an unpacked array element (`mem[3]`) ... `coarse_fallback=false`".
- **Severity rationale**: over-conservative disclosure (`coarse=true` tells the agent to downgrade), not a false `verified`, hidden uncertainty, or wrong value; count/value/driver are correct in both forms. P2, not P1.
- **Fix direction**: pass `query_sig` (the resolved id) to `query_precision` instead of `sig`, or normalize the lookup; add a regression assertion for a relative-form array-element query. Must re-verify packed-bit cases in §2 remain identical (they will: resolved ids for `top.y[5]` etc. carry no `array_element`).
- **Test gap**: new test only covers the exact-form query `top.mem[0]`.
