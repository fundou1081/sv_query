### P1 — False capability claim: IR bridge and collector are orphaned; legacy tree is still functional

- **Where**: `docs/dev/CLAIMS.md:88` (C-66); `docs/dev/EXPRESSION_IR.md:212-213,224`; orphan code `src/sv_query/trace/core/graph/viz/expression_ir_bridge.py:30-58` (no production importer); live legacy consumers `src/sv_query/trace/unified_tracer.py:537,737-759` and `src/sv_query/trace/core/extractors/expr_tree_builder.py:40-57,158-159`.
- **Repro (read-only)**:
  1. `grep -rn "expression_ir_bridge\|ir_to_tree\|collect_ir" src/sv_query` → only self-references inside the bridge file (plus `.pyc`). No CLI/session/viz/extractor imports it.
  2. Build a ternary RTL graph: `_emit_conditional_op_nodes()` emits `OP_TERNARY` nodes from `_expr_trees`; deleting the legacy tree would remove functional graph nodes, not just display.
  3. `collect_from_tree()` (legacy) still writes `result.const_map` / `result.func_info`; `collect_ir()` writes nothing in production.
- **Impact**: The claim says the typed IR is the exposed source for viz and const/call extraction and that the syntax tree is display-only. In reality, IR is exposed only as a `DriverInfo` snapshot; the viz tree and const/call pipeline remain legacy-tree driven. A downstream worker trusting C-66/§9a could remove the "display-only" tree and break ternary/case node emission and const/func extraction. This is a false capability claim ("false verified" class, protocol §4), not a runtime crash.
- **Fix (implementer, then re-audit)** — choose one:
  - **(a) Honest scope (minimal)**: reword C-66 to e.g. *"P198.6 adds `DriverInfo.expression_ir` from edge `expr_id` plus an IR→viz-tree bridge and IR const/call collector that are available but not yet wired; legacy syntax tree remains functional for const/func extraction and conditional-op emission until P198.9"*; reword `EXPRESSION_IR.md:212-213,224` to say the bridge exists and migration of consumers is deferred to P198.9; keep status `scoped`.
  - **(b) Wire the migration**: make viz rendering call `ir_to_tree()` and make `expr_tree_builder`/`graph_builder` populate `const_map`/`func_info` via `collect_ir()` from the IR, with graph-baseline + CLI/session parity tests proving identical behavior; then re-audit as a semantic change (iron rule 14).
- **Test gap**: no test asserts that any production viz output or `const_map`/`func_info` entry originates from IR; no test asserts the legacy tree's functional consumers are preserved. Add such tests under (b), or a docs/claim test under (a).
- **Verdict impact**: blocking. No merge/release while open.
