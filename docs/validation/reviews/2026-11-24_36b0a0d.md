## Findings

### P1-1 — x/z shift literal silently becomes shift amount 0 (wrong fanin/fanout)
File: `src/sv_query/trace/core/driver_extractor.py:1027-1035` (`_semantic_int_literal`), consumed at `:1115-1116` and `src/sv_query/trace/core/query/signal.py:832,934`.
Repro (read-only, opencode temp dir):
```python
# assign y = a << 4'dx;   (a [7:0], y [9:0])
e = tracer.get_graph().get_edge("top.a", "top.y")
e.source.shift_amount                      # -> 0        (WRONG; should be None/unknown)
tracer._signal_tracer._expr_source_bits(e, "top.y", 2)  # -> ['top.a[2]']  (WRONG; SV result is all-x)
```
Root cause: pyslang `SVInt.__int__()` maps x/z bits to 0. The `SVInt` object exposes `hasUnknown()` (verified via `dir()`), so the constant is *not* determinate. The `try/except (TypeError, ValueError)` does not catch this because no exception is raised. This is a silent wrong answer reachable with legal SV, the same failure class as the original bug (wrong bit mapping), and it violates the stated "unknown, not wrong" contract (checklist item 3) and iron rules 2/13.
Fix: in `_semantic_int_literal`, after confirming `IntegerLiteral`, check `expr.value.hasUnknown()` and return `None` before `int(...)`; keep the existing exception guard for non-int-convertible values. Add a test for `a << 4'dx` (and `4'dz`) asserting `shift_amount is None` and `_expr_source_bits(...) is None`.
Test gap: the committed test covers only sized-decimal `4'd2` and dynamic `b`; no x/z, non-decimal-unknown, or `hasUnknown` assertion.

### P2-1 — conversion/cast-wrapped left operand loses the semantic shift amount
File: `src/sv_query/trace/core/driver_extractor.py:1111-1116` (uses `rhs_expr.right` on the un-unwrapped node).
Repro: `assign y = $signed(a) >>> 4'd2;` → `rhs_expr.kind='ExpressionKind.Conversion'`, `rhs_expr.right` is `None`, so `shift_amount=None` and `_expr_source_bits(edge,'top.y',2)` is `None`, even though the semantic AST has the literal in the unwrapped root's `right` (the same root `_detect_binary_op` already finds at `:887-890`). Same for `(a + 128) >>> 8`. Note the models.py docstring's canonical example is exactly `$signed(a) >>> b[4:0]`.
Impact: safe (unknown, not wrong) but a capability loss for a documented expression shape. Fix: unwrap `rhs_expr` with the same logic as `_detect_binary_op` before reading `.right` (reuse `unwrap`/single helper — iron rule 8). Test gap: no conversion-wrapped shift test.

### P2-2 — bit-select left operand leaves `operand_side` empty, so `shift_amount` is dropped
File: `src/sv_query/trace/core/driver_extractor.py:1113-1114` gating on `operand_side == "left"`, coupled with `_detect_binary_op:913-945` (slice operand not matched to the leaf signal).
Repro: `assign y = a[7:0] << 4'd2;` → `signal='a'`, `operand_side=''`, `shift_amount=None` although `rhs_expr.right.kind='ExpressionKind.IntegerLiteral'`. Largely a pre-existing operand-detection limitation now inherited by the new field; safe (unknown) but incomplete. Fix: make shift-amount extraction independent of `operand_side` (the right operand of a shift is the amount regardless of which side the traced signal is on), or fix slice-side matching. Test gap: no bit-select shift test.

### P2-3 — committed tests do not lock the full stated operator/literal matrix
File: `sim/tests/unit/test_p197_4_shift_semantic.py` (only 2 tests: `<<` + `4'd2`, and `a << b`).
The fix works for all four operators and for unsized/`8'd3`/`4'h2`/signed literals (verified manually), but none of that is regression-protected. Checklist items 1 and 4 are therefore satisfied by implementation, not by tests. Fix: parametrize the test over `<<, >>, <<<, >>>` and over `2, 8'd3, 4'h2, 4'd2`, and assert fanout inverse for the dynamic case. (Not blocking on its own, but it would have caught P1-1.)

## What is correct (to avoid false positives)

1. The reported bug is fixed: `a << 4'd2` yields `shift_amount=2` and mapping `y[2]→a[0]`, `y[4]→a[2]`, `y[6]→a[4]`, with the exact inverse for fanout. The old code would read `k=4` (literal width) and return `[]` for y[2].
2. All four shift operators use the semantic `op` enum consistently: `shift_amount` set for `LogicalShiftLeft/Right`, `ArithmeticShiftLeft/Right` (driver_extractor) and the same four in `_EXPR_SHIFT` (signal.py); direction via `op in (...Left...)` is correct for both fanin (`pos-k`) and fanout (`pos+k`).
3. Unsized `2`, `8'd3`, `4'h2`, `4'sd2` all yield the *value* not the width. Large literals stay Python ints; no `OverflowError`.
4. Dynamic `a << b` and non-literal `a << (2+1)` return `None` for both amount and mapping — explicit unknown, never a guessed number.
5. No source-regex substitute remains for shift in `query/signal.py`; no node-id/name guessing was introduced. Single implementation (iron rule 8).
6. Serialization is forward/backward compatible and needs no MIG bump: field list is derived from `dc_fields`, `asdict` emits the field, `from_dict` filters unknown keys and the new field defaults to `None`.
7. Tests genuinely fail on revert, including the mapping assertion under a signal-only revert (`assert [] == ['top.a[0]']`).
8. Prior-fix regression: P197.3 had no P1; its P2-1 (gate-red unused imports) was closed in parent `47a01c25`. Non-pytest gates including cumulative lint and `check_semantic_regex.py` are green.
