## 2. Findings

### R1 — Regression test is NOT revert-sensitive (P2, introduced by this commit)
- Location: `sim/tests/unit/test_p194_5_12_ports_reg.py:12-25`; its docstring claims
  "output reg ports stay in `ports`".
- Repro: the fixture `module top(input logic a, output reg y); always_comb y = a; endmodule`
  produces node `top.y` of kind **`PORT_OUT`**, not `REG` (verified via `graph nodes`).
  Therefore the old `port_kinds` check already includes it.
- I ran the **parent** `ports.py` (`git show 1246f404:…/ports.py`) in an isolated temp root
  against the same fixture: parent output `count=2`, `y direction=output` — the new test
  **passes on the parent**. On SERV the same parent code gives `count=27`, no `o_new_irq`,
  so the behavioral fix is real but is *not* exercised by the added test.
- Impact: the only regression guard for this fix is vacuous; a future revert would not be
  caught by this test. This violates CODE_REVIEW_PROTOCOL §3.5 ("new tests fail if the fix
  is reverted; fixtures actually exercise the claimed path").
- Severity P2 (coverage/gate debt), not P0/P1: product behavior is correct and unchanged
  outputs are honest.
- Fix: replace/augment with a fixture that actually yields a `REG`-kind port carrying
  `extra.direction` — e.g. a SERV-derived fixture, or assert on a generated-instance
  `output reg` port. Add a `graph nodes` assertion that the port node kind is `REG` so the
  test cannot silently continue testing the PORT_OUT path.

### R2 — `extra.direction` fallback does not cover top-level `output reg` ports (P2, pre-existing / out-of-scope, caveat only)
- Repro: `module top(input clk, input a, output reg y); always_ff @(posedge clk) y <= a;`
  → node `top.y`: `kind=REG`, `is_port=True`, `extra={}` (driver-extractor top-level port
  creation does not set `extra.direction`). Both parent and current `ports` report
  `count=2` (missing `y`).
- So the commit message "include output-reg ports in ports listing" and the test docstring
  overstate generality: the fix works only for instance ports that carry `extra.direction`
  (the SERV csr generate path). This is a pre-existing limitation, not a regression
  introduced here, and it is outside the stated P194.5.12 scope.
- Suggestion (follow-up, not a blocker for this item): fall back to `get_port_declarations()`
  direction (or the `driver_extractor` port metadata) when `extra.direction` is absent, so
  the "output-reg ports" claim is true generally. Track as a separate item.

No P0 or P1 finding. No silent wrong answer, no fabricated `verified`, no stale state, and
no duplicate/wrong node inclusion in the audited scope.
