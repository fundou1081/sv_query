# 长程结构查询：12-task 对照结果

**日期**: 2026-11-05
**PLAN**: P69
**模型**: MiniMax-M3 / DeepSeek-Flash
**任务**: 12 个，覆盖 AXI / SERV / PicoRV32
**原始数据**: [long_range_12_2026-11-05.json](long_range_12_2026-11-05.json)
**评分**: [score_long_range.py](../../tools/benchmark/score_long_range.py)

> 4-task pilot 见 [LONG_RANGE_PILOT_2026-11-05.md](LONG_RANGE_PILOT_2026-11-05.md)；
> 本文件是扩展后的结果，结论以本文件为准。

## 1. 协议

- **source 臂**：源码 copy 在 `/tmp/lr_pilot`，运行时全局 `sv_query` 二进制已临时移走；
  要求只读源码/grep，最多 8 次工具调用。
- **svq 臂**：同一源码 copy，`sv_query` 可用；其余条件相同。
- 每题要求 exact canonical ID / path / count；
  评分脚本确定性比较，不调用模型。
- 12 题 × 2 模型 × 2 臂 = **48 个 agent**。

## 2. 总表

| 模型 / 臂 | Exact | 高置信错误 | 平均 wall time |
|---|---:|---:|---:|
| MiniMax-M3 / source | **7/12** | **2/12** | 51.4 s |
| MiniMax-M3 / svq | **11/12** | **1/12** | 145.3 s |
| DeepSeek-Flash / source | **6/12** | **1/12** | 57.2 s |
| DeepSeek-Flash / svq | **11/12** | **0/12** | 74.8 s |

## 3. 按设计族

| 族 | MiniMax source | MiniMax svq | DeepSeek source | DeepSeek svq |
|---|---:|---:|---:|---:|
| AXI（4 题） | 4/4 | 4/4 | 2/4 | 4/4 |
| SERV（4 题） | 1/4 | 4/4 | 2/4 | 4/4 |
| PicoRV32（4 题） | 2/4 | 3/4 | 2/4 | 3/4 |

两个模型 **with svq 后都到 11/12**；剩下的同一个失败点是
`pico_adapter_rdata_fanin` 的 bit `[16]` 查询。

## 4. 典型错误

### source-only

- AXI：把 `axi_adapter.m_axi_araddr` 的父端口连接误算成 driver，或把 load 判空。
- SERV：把 **terminal fanout** 当成 direct fanout（12 vs 8）；
  把 `serv_rf_top.cpu` 实例节点当成 path 节点；
  漏掉/误加 generate 内的 CSR。
- Pico：ID 写成 `file:line`；把 `picorv32_core.mem_valid` 当成 adapter 的直接 driver；
  把 `xfer_done` 的 6 个 canonical load 按源码行拆成 7 个。

### svq

- 唯一的系统性失败：`picorv32_axi.axi_adapter.mem_rdata[16]` 的 bit 查询。
  两个模型都通过 `drivers` 拿到 `bit_base_fallback`/count=0，然后退回到
  32-bit 父端口 `mem_axi_rdata`；source 臂反而给出了 `[16]` bit 节点。
- 说明这是 **CLI 解析/bit fallback 行为** 需要修，不应简单归因于模型。

## 5. 成本

`svq` 臂没有变便宜：

- MiniMax：51.4 s → 145.3 s；
- DeepSeek：57.2 s → 74.8 s。

原因主要是 agent 会多跑验证命令、查看 graph edges/profile/verify，
以及 `sv_query` cold build。这里没有 token/tool-call 统计，也没有拆分
cold build / warm query；**不能把 wall time 当作最终成本结论**。

## 6. 可信度

支持：

- 在这 12 题上，sv_query 臂把 exact 准确率从 **6–7/12** 提升到 **11/12**；
- 两个模型都给出一致的、可核对的 canonical ID/path；
- 工具减少了“源码上找错端口/把 terminal fanout 当 direct”的错误。

不支持：

- “准确率提升 X%”的总体结论（12 题、单 seed、任务手工挑选）；
- “成本更低”；
- “模型能力排名”；
- HWE-Bench/VeriBugBench 或修复任务结论。

## 7. 仍然存在的实验缺陷

1. **source 臂仍不干净**：即使二进制移走，MiniMax 的某些输出仍引用了
   `/Users/fundou/my_dv_proj/sv_query` 里的 `connection_extractor.py` 规则。
   它不是纯“只有源码”的控制组。
2. **没有 token/tool-call 统计**：workflow 结果只拿到 wall time。
3. **单 seed**：无重复运行。
4. **bit fallback 未修**：两个 svq 臂在同一个 Pico bit 任务上失败。
5. **Ground truth 非双盲**：由源码 + sv_query 双来源建立。
6. **任务难度不均**：AXI 对 MiniMax source 很容易，SERV/Pico 更能区分。

## 8. 结论

这轮比 4-task pilot 更清楚：

> **sv_query 的主要价值是减少结构事实错误和模型间差异，而不是降低单次调用时间。**
> 两个模型带工具后都达到 11/12；但工具本身还有 bit fallback 缺口，且 agent
> 的验证行为会把 wall time 拉长。

在修掉 bit fallback、改为 token/tool-call 计量、并完成真正的 source 隔离前，
这仍是**内部验证**，不应写进对外性能/能力声明。
