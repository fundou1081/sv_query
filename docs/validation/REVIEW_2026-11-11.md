## 3. 为什么严格纪律没有拦住

### 3.1 纪律覆盖“形式”，没有覆盖“语义”

现有 8 个门禁检查的是：

```text
文件是否存在、注册是否完整、层方向、regex 位置、CC 阈值、
计划格式、文档链接、异常写法
```

它们不检查：

```text
一条路径是否真的是数据路径
两个构建是否产生同一张图
verified 是否覆盖了全部节点
SPI corpus 是否被执行
snapshot 是否与 live 同构
```

所以：

```text
gate 全绿 ≠ 语义正确
```

这是纪律的**覆盖边界**，不是执行不认真。

### 3.2 测试是实现的镜像，不是独立的规格

- P152 的 expected 大量由 CLI 反向生成；
- `test_path_directed_parity` 只证明 `paths` 与 `dataflow` **一致**，不证明它们**正确**；
- bit/reciprocity 只有“没有误报”的测试，没有 true-positive；
- 关闭检查后测试仍绿，说明测试没有验证检查本身。

这会产生“自我确认”：

```text
实现有 bug → 测试按实现写 → 测试通过 → 认为实现正确
```

### 3.3 指标替代了目标（Goodhart）

- “0 skipped” 被当成质量提升，但 P157 是把失败测试移出统计；
- “canonical passed count (see INDEX; historical)” 被当成能力证明，但没有执行 SPI corpus；
- “APPROVE WITH NITS” 被当成真实项目通过，但 worker 的 fresh/snapshot 只跑了一次；
- “canonical 全绿” 被当成可提交，但 CI 的 lint 是 no-op，CI 测试集也不同。

### 3.4 边界概念没有唯一定义

同一个词在不同层有不同实现：

| 词 | 实际含义 |
|---|---|
| `directed` | PathResolver：所有边；SignalTracer：DRIVER/CONNECTION；frontier：再加 BIT_SELECT |
| `verified` | total==0 且 status known，不考虑 truncated |
| `snapshot supported` | 有的命令支持，有的不支持；没有 capability 矩阵 |
| `done` | 代码+测试+文档，不含语义 claim 的反证 |
| `independent worker` | 访问独立，但代码/快照/假设共用 |

这不是“执行歧义”那么简单，是**缺少单一语义契约**。

### 3.5 局部修复没有全局不变量

- P151 加了 MIG 持久化，但没有统一 snapshot 构造路径；
- P154 按需给 3 个命令加 snapshot，形成 9 vs 8；
- P157 为了 0 skip 把测试移走，没有先问“这些测试为什么失败”；
- P155 修了 reciprocity，但没有加 true-positive 测试防止复发。

每次修复都局部正确，但都绕过了“全局不变量”的检查。

### 3.6 真实项目证据不可重复

- filelist 靠人工 4 轮补；
- snapshot 是外部 `/tmp` fixture；
- 构建不确定；
- 没有 dependency-closure 自动解析；
- 没有 real-project corpus runner。

所以“真实项目验证”目前是**一次性的 worker 证据**，不是可重复 gate。

### 3.7 完成判定过早

`AGENTS.md` 的完成判定是：

```text
代码 ✅ + 测试 ✅ + 文档 ✅
```

但没有要求：

```text
claim 可反证
真实 corpus 执行
确定性
边界/截断语义
```

P147/P152 都在这个缺口里被标成完成。

## 4. 结论：是纪律漏洞，还是执行歧义？

**两者都有，但主因是纪律漏洞，不是执行不认真。**

更准确地说：

```text
流程纪律：执行得好
语义纪律：基本缺失
证据纪律：不足
指标纪律：被 Goodhart 化
```

执行层面确实有歧义，但歧义集中在**没有定义的语义边界**：

- 什么算数据边？
- 什么叫 verified？
- snapshot 支持的范围是什么？
- 什么叫“完成”？
- worker 的“独立”到底独立到什么程度？

这些不是靠“更严格地执行现有规则”能解决的，因为现有规则没有覆盖它们。

## 5. 解决机制：从“流程门禁”升级为“语义门禁”

不是再写 10 条口号，而是建立 4 层可执行机制。

### 5.1 每个不变量必须有 executable contract

把 I1~I5 映射到可执行检查：

| 不变量 | 当前漏洞 | 新 gate |
|---|---|---|
| I1 只读 | filelist prune 覆盖 RTL | 写入路径运行时检查 + `--apply` + 测试 |
| I2 稳定 schema | 40/40 未覆盖 | registry contract test + schema snapshot |
| I3 单一实现 | 三套 edge policy / snapshot 双构造 | 共享常量 + parity + 一处构造入口 |
| I4 降级显式 | truncated verified | verified 状态机测试 + unknown/truncated |
| I5 可观察后果 | 文档漂移 | claim ledger + docs 检查扩展 |

**规则**：

```text
不能写成测试的规则 = guideline，不是 gate。
```

### 5.2 每个 gate 必须有“反事实测试”

对每个检查器/验证器：

1. 构造一个真实违规输入；
2. 断言它必须红；
3. 关闭/破坏实现，断言测试必须红。

bit/reciprocity 当前就是反面教材：关闭检查测试仍绿。

### 5.3 独立 oracle

不要用同一实现生成 expected。

- 小型 fixture：手写期望图/路径；
- 真实项目：从 RTL 测试计划或人工 golden 生成 expected；
- P152 corpus：固定 expected，不由 CLI 反向生成；
- 路径/verify：用“应当不存在”的反例（CLOCK/RESET）作为 oracle。

### 5.4 可重复性与有界性作为一等公民

- 同一输入 N 次构建 canonical hash 一致；
- 所有长查询有 work budget + wall-clock timeout；
- 超限显式 `truncated`，绝不静默截断；
- snapshot corpus 进 canonical，不能只靠 worker。

### 5.5 指标重新定义

报告不要只写：

```text
canonical passed count (see INDEX; historical) / 0 skipped
```

要写：

```text
passed
failed
unknown
truncated
unexecuted
skipped-with-reason
external-not-run
```

“0 skipped”不再是 KPI。

### 5.6 变更纪律

每个修复必须回答三个问题：

```text
1. 这个修复改变了哪个语义契约？
2. 如果它是错的，哪个测试会红？
3. 哪个独立 oracle 能证明它？
```

没有答案的修复，只能算实验，不能标完成。

### 5.7 评审纪律

worker 评审不能只看“APPROVE”。

要求：

- 给出可复现命令；
- 给出反例；
- 明确区分“我观测到”和“我推断”；
- 主会话至少独立复现 P0；
- 不再把一次 fresh parse 当 determinism 证明。
