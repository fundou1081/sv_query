## 💡 关键发现 / 战略结论 (最重要的一节)

1. **这不是"技巧问题", 而是"批次跨度问题"**: 5 次尝试 (正则/更小范围/AST) 都失败,
   共同点是**一次改一整层**。`strict` 是一个**横切关注点**, 牵动: CLI 选项 → helper 形参
   → 包装调用链 → 核心 `self._strict` 语义分支 → 61 文件的调用点。**任何"一次性"改法
   都会留下未覆盖的执行路径**。
2. **可行的推进方式 (建议)**: 放弃"一次改一层", 改成**"一个文件一次提交"**:
   - 每次只改**一个文件** (先 `handshake.py` — 含唯一位置实参), 其余文件保持原样;
   - 改完立刻: `scan_strict` 复测数字下降 + 跑该文件相关用例 + 全量门禁;
   - 绿 → 提交; 红 → 回退该文件并单独诊断。
   以 61 文件计, 这是 ~60 次小提交, 但**每次都是可验证的**, 不会再出现"改了 5 次全回退"。
3. **换工具也只是辅助**: AST 解决了"形态穷举", 但解决不了"**调用链同步**"与
   "**语义分支**" —— 这两者需要**运行时反馈**, 即真正的测试驱动逐文件改造。
4. **核心层的 `self._strict` 必须单独设计**: 它控制"raise vs 返回 partial AST",
   删除它 = 删降级分支 = 行为变更 (会暴露 fixture 真错, 与批次 5 绑定)。
